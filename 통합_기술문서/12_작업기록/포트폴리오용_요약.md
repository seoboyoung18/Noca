## 백엔드 주요 구현

### 비동기 워커 7종 (PostgreSQL 큐)

요청은 큐에 넣고 즉시 응답, `@Scheduled` 워커가 처리한다.

```
조건부 UPDATE (QUEUED → PROCESSING) + 부분 UNIQUE 인덱스 7개
WHERE status IN ('QUEUED','PROCESSING')
```

`processing-timeout` 이 지난 행은 고아로 보고 종결한다.
**반복 실패는 큐에 되돌리지 않고 `ABANDONED` 로 끝낸다** — "영영 실패하는 건이
매 주기 GMS 크레딧을 태운다."

### AI 콜백 멱등성 3단 검증

AI가 콜백을 최대 4회(0·1·5·20초) 보낸다. 막지 않으면 **분석 한 번에 견적 4개**가 된다.

| 단계 | 검사 |
| --- | --- |
| 1 | 헤더 `X-Request-Id` == 본문 `requestId` |
| 2 | 경로 `jobId` == 본문 `jobId` |
| 3 | 저장된 `requestId` 일치 (철 지난 콜백 차단) |

이미 끝난 작업이면 저장을 생략하고 `200 duplicate=true` 로 재시도를 멈춘다.

### 내부 API 2중 방어

`SecurityConfig` 가 `/internal/**` 을 `denyAll()` 하고 **콜백 하나만** `permitAll()` 로 연다.
그 하나도 컨트롤러가 `X-Internal-Token` 으로 다시 검증한다.
여기에 사설 IP 바인딩이 더해져 2겹이다.

### REST API 98개 · 도메인 18개

`src/main` 519파일. 컨트롤러 33개.

## AI 주요 구현

### 분석 오케스트레이션 (`POST /analyze`)

추론 → ROI 임베딩 → pgvector 검색 → 견적 산출을 잇고 **콜백 1회**로 끝낸다.
어느 단계에서 끊기든 백엔드가 작업의 끝을 알 수 있게 예외를 계약상 4개 코드로 좁혔다.

### 검색 완화 3단계

`MODEL` → `PRICE_TIER` → `ALL`. 결과의 `fallbackStage` 를 `estimate_item.ref_condition` 에
저장해 화면이 "얼마나 비슷한 사례인가" 를 보여 준다.

### 부품 미확정 정책

부품을 못 붙인 검출은 `partCode = null` · `VECTOR_ONLY` 로 남기고 **견적 항목에서 뺀다.**

> 부품을 틀리게 부여하는 것보다 null 이 견적 안전성 측면에서 낫다.

정확도보다 **안전을 택한 의식적 선택**이다.

### 오프라인·온라인 전처리 통일

`shared/vision` 을 파이프라인과 AI 서버가 공유한다.
ROI 20% padding · 224px letterbox · L2 정규화가 양쪽에서 동일하다.

전처리가 갈라지면 **오류 없이 검색 결과만 틀린다.** `embedding_model_version` 불일치 시
검색을 거부하는 장치도 뒀다.

## 대표 문제 해결 사례 3개

### ① 마이그레이션 가드가 영영 통과하지 못하는 문제

**상황**: `ddl-auto=validate` 로 스키마 사고를 막으려 CI 가드를 넣었다.

**문제**: SQL을 적용한 뒤 파이프라인을 재실행해도 가드가 또 멈췄다.

**원인**: 가드는 "마지막 배포 커밋 이후 바뀐 SQL" 을 찾는데, **배포가 실패하면
`DEPLOY_MARK` 가 갱신되지 않아** 같은 SQL이 계속 잡혔다.

**해결**: "코드 배포 상태" 와 "스키마 적용 상태" 를 **다른 축**으로 보고 적용 완료 원장을
따로 뒀다. 경로만이 아니라 **내용 해시**까지 적어, 적용 후 SQL이 바뀌면 다시 멈추게 했다.

**근거**: 커밋 `a560f93`, `.gitlab-ci.yml` 주석

---

### ② AI 메모리가 DB를 끌고 내려가는 구조

**상황**: 예산 제약으로 AI 서버와 운영 PostgreSQL이 **같은 박스**에 있다(15GB, swap 0).

**문제**: YOLO 2종 + DINOv2가 메모리를 먹으면 DB가 OOM으로 죽는다. DB가 죽으면
`ddl-auto=validate` 때문에 **백엔드도 재기동을 못 한다.** 전체 장애다.

**해결**:
- AI 컨테이너에 `--memory=6g --memory-swap=6g --cpus=3` 강제
- 이 상한을 "선택이 아니다" 라고 CI 주석에 🔴 로 명시
- `-XX:+ExitOnOutOfMemoryError` — "OOM 뒤에 반쯤 죽은 채로 살아 있으면 헬스체크는
  통과하는데 요청만 실패한다"

**근거**: `.gitlab-ci.yml` · `backend/Dockerfile` 주석

---

### ③ `/dev/shm` 64MB로 인덱스 생성이 실패

**상황**: 2026-09-21, v2 corpus 이관에서 304,114건 벡터의 HNSW 인덱스를 재생성해야 했다.

**문제**:

```
ERROR: could not resize shared memory segment to 2144374176 bytes: No space left on device
```

**분석**: 디스크도 메모리도 남아 있었다(**14GB 여유**). 원인은 컨테이너의 `/dev/shm` 이
도커 기본값 **64MB** 라는 것이었다. pgvector HNSW **병렬** 빌드가
`maintenance_work_mem`(2GB) 크기만큼 공유 메모리를 여기에 잡으려 했다.

**해결 선택지 비교**:

| 안 | 문제 |
| --- | --- |
| `--shm-size` 확대 | **운영 DB 컨테이너 재생성 필요** — 1.15GB 데이터가 걸려 있어 기각 |
| `maintenance_work_mem` 을 64MB 미만으로 | 빌드가 극도로 느려짐 |
| **병렬 빌드 끄기** | 채택 — 프로세스 전용 메모리를 쓴다 |

```sql
SET max_parallel_maintenance_workers=0;
SET maintenance_work_mem='2GB';
CREATE INDEX ix_roi_hnsw ON repair_case_roi_embedding USING hnsw (embedding vector_cosine_ops);
```

단일 스레드라 30분~1시간이 걸렸지만 안전하게 끝났다.

**결과**: 건수 대조 5개 항목 전부 일치. `repair_case.model_id` 커버리지가
**0건 → 80,919/93,964 (86.1%)** 로 올라 `MODEL` · `PRICE_TIER` 검색 단계가 살아났다.

**근거**: 2026-09-21 작업 실측

## 이력서용 성과 문장 5개

> **1.** 사고 사진 → YOLO 손상 검출 → DINOv2 ROI 임베딩 → pgvector 유사 사례 검색 →
> 수리비 산정으로 이어지는 AI 분석 파이프라인의 백엔드를 설계·구현했습니다.
> 수리 사례 93,964건, ROI 벡터 720,668건 규모입니다.

> **2.** 메시지 브로커 없이 PostgreSQL 조건부 UPDATE와 부분 UNIQUE 인덱스로 작업 큐를
> 구현해, 워커 7종의 중복 실행을 DB 수준에서 차단했습니다.

> **3.** Spring Boot·FastAPI 컨테이너화와 GitLab CI 3잡 자동 배포를 구축하고,
> 레이어드 jar 분해로 배포 전송량을 97MB에서 8.9MB로 줄였습니다.

> **4.** `ddl-auto=validate` 환경에서 스키마 불일치로 앱 전체가 기동 실패하는 사고를 막기 위해,
> 내용 해시 기반 적용 원장을 쓰는 CI 마이그레이션 가드를 설계했습니다.

> **5.** 운영 corpus 1.15GB를 무중단 절차로 이관하며 `/dev/shm` 제약으로 인한 pgvector HNSW
> 인덱스 생성 실패를 진단·해결하고, 차종 매핑 커버리지를 0%에서 84%로 올려 검색 완화 단계를
> 정상화했습니다.
