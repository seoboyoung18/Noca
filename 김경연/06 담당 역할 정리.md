# ML/Data Pipeline + Image Retrieval

**: 대규모 차량 사고 데이터를 정제·연결하여 검색 가능한 형태로 만들고, 입력된 파손 이미지와 유사한 과거 수리 사례를 찾아내는 역할**

- 원본 이미지·라벨·견적 데이터를 하나의 사고 사례 단위로 연결
- 이미지 임베딩 생성
- Vector DB 검색 및 Retrieval 성능 평가

## 전체 담당 흐름

```
원본 이미지·라벨·견적 데이터
        ↓
HDFS 저장 및 Spark 전처리
        ↓
사고 단위 데이터셋 구성
        ↓
이미지 Encoder 선정·비교
        ↓
Embedding Batch 생성
        ↓
Vector DB + Metadata DB 적재
        ↓
신규 파손 이미지 Top-K 검색
        ↓
Retrieval 성능 평가
        ↓
유사 사례의 수리 방식·비용 조회
```

## 1. 원본 데이터 분석 및 정제

- 이미지, Segmentation 라벨, 견적 JSON 구조 분석
- `image_id`, `case_id`, 차종, 부위, 손상 유형, 수리 내역 등 공통 필드 정의
- 깨진 파일·결측값·중복 이미지 검증
- 서로 다른 부품명과 작업명 표준화

```
앞범퍼 / 후론트범퍼 / 프런트범퍼
→ FRONT_BUMPER
```

하나의 사고에 여러 이미지와 하나의 견적서가 연결되므로, 개별 이미지보다 **`case_id`를 중심으로 데이터를 관리**한다.

## 2. 학습·검색용 데이터셋 생성

전체 이미지에서 목적에 따라 데이터셋을 분리한다.

- 파손 분석 모델용 데이터셋
- 이미지 유사도 검색용 데이터셋
- 견적 및 수리 내역 조회용 데이터셋
- 견적서와 연결된 약 12만 장을 Retrieval 후보군으로 선별

같은 사고의 사진이 학습 데이터와 평가 데이터에 동시에 포함되지 않도록 **`case_id` 기준으로 Train/Validation/Test를 분리**하여 데이터 누수를 방지한다.

## 3. 이미지 유사도 검색

### 임베딩 모델 선정

차량 전체의 색상이나 배경보다 **파손 부위·손상 형태가 비슷한 사례**가 검색되도록 Encoder와 입력 방식을 비교한다.

- 전체 이미지와 파손 부위 Crop 비교
- 사전학습 Encoder별 Retrieval 성능 비교
- 필요 시 차량 파손 데이터에 맞게 Fine-tuning
- 이미지 특징과 차종·부위·손상 유형 메타데이터를 결합한 검색 구성

### 검색 파이프라인

```
신규 차량 이미지
   ↓
파손 부위 분석 및 Crop
   ↓
Embedding 생성
   ↓
차종·부위·손상 유형 필터링
   ↓
Vector Search
   ↓
유사 사고 사례 Top-K
```

검색 결과에는 다음 정보를 함께 반환한다.

```json
{
  "image_id": "IMG_001",
  "case_id": "CASE_001",
  "part": "FRONT_BUMPER",
  "damage": "SCRATCH",
  "similarity": 0.91
}
```

## 4. Vector DB 구축

견적서와 연결된 이미지의 임베딩을 배치로 생성하고 검색에 필요한 메타데이터와 함께 Vector DB에 적재한다.

| 구분 | 저장 정보 |
| --- | --- |
| Vector | 이미지 Embedding |
| 식별 정보 | image_id, case_id |
| 검색 조건 | 차종, 부위, 손상 유형, 심각도 |
| 참조 정보 | 이미지 경로, 견적 연결 여부 |

대규모 이미지의 임베딩 생성과 재생성이 가능하도록 배치 파이프라인을 구성한다. Encoder가 변경되면 전체 임베딩을 다시 생성하고 버전별 검색 성능을 비교할 수 있도록 관리한다.

## 5. Retrieval 성능 평가

검색 성능은 단순히 이미지가 눈으로 비슷한지만 보지 않고, **실제 수리 판단에 도움이 되는 사례가 검색되는지**를 기준으로 평가한다.

- 동일·유사 파손 부위 검색 비율
- 동일·유사 손상 유형 검색 비율
- 유사 수리 방식 검색 비율
- Recall@K, Precision@K, mAP 등 Retrieval 지표
- 메타데이터 필터 적용 전후 성능 비교
- 실제 검색 결과에 대한 정성 평가

이미지와 견적서의 개별 수리 항목이 직접 연결되어 있지 않으므로, 초기 평가는 **사고 사례 단위의 수리 내역 유사성**을 기준으로 구성한다.

## 6. 견적 데이터 정제 및 검색 결과 연결

원본 견적 JSON에서 부품명·작업명·비용을 정규화하고 `case_id`를 기준으로 검색 결과와 연결한다.

```
Vector DB Top-K
      ↓
유사 case_id
      ↓
견적·수리 내역 DB 조회
      ↓
수리 방식 분포 및 비용 범위 계산
```

현재 데이터는 이미지의 특정 파손 부위와 견적서의 개별 항목이 직접 매핑되어 있지 않다. 따라서 초기에는 **유사 사고의 전체 수리 내역과 비용 범위**를 제공하고, 이후 매핑 규칙이나 추가 라벨이 확보되면 부위별 비용 분석으로 확장한다.

## 7. 모델 담당자와의 인터페이스

파손 분석 모델의 출력 결과를 Retrieval 입력과 연결할 수 있도록 데이터 규격을 협의한다.

```json
{
  "image_id": "IMG_001",
  "part": "FRONT_BUMPER",
  "damage": "SCRATCH",
  "bbox": [120, 80, 410, 360],
  "confidence": 0.93
}
```

| 파손 분석 모델 담당 | 나 — Data Pipeline & Retrieval |
| --- | --- |
| 부품·손상 탐지 모델 학습 | 원본 데이터 파싱·정제 |
| Segmentation 성능 개선 | case_id 기준 데이터셋 분할 |
| 파손 영역 bbox/mask 생성 | Retrieval Encoder 선정·비교 |
| 추론 결과 규격 협의 | 임베딩 배치 생성 |
|  | Vector DB 및 메타데이터 설계 |
|  | Top-K 검색 로직 구현 |
|  | Retrieval 성능 평가 |
|  | 견적 데이터 정규화 및 검색 결과 연결 |
|  | HDFS·Spark 기반 재현 가능한 파이프라인 구축 |
