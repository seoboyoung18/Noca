# 대규모 Wafer Map 기반 유사 패턴 검색 및 Lot 분석 시스템

> **현재 Wafer와 형태적으로 유사한 과거 Wafer를 검색하고, 유사 패턴이 특정 Lot에 집중되는지 분석하여 엔지니어가 우선 조사할 생산 범위를 제공하는 시스템**
> 

### 아이디어 개요

- 반도체 제조에서는 Wafer의 **불량 위치·분포·형태(Spatial Pattern)**를 통해 생산 이상을 파악할 수 있음.
- 같은 불량 유형이라도 세부적인 형태가 다를 수 있어, 단순 불량 분류를 넘어 **형태적으로 유사한 과거 Wafer를 검색**
- 검색된 Wafer가 특정 Lot에 집중되는지, 여러 Lot에서 반복되는지 분석하여 **문제가 발생한 생산 범위를 좁히는 데 활용**
- 불량 원인을 직접 판단하는 것이 아니라 **유사 사례와 우선 조사 Lot을 제공하는 의사결정 지원 시스템**
- **기획의 필요성 이해를 위한 그림 ㅎㅎ;;**
    
    ```jsx
    ┌────────────────────────────────────────────────────────────────────────┐
    │                        [ 반도체 생산 단위 구조 ]                        │
    └────────────────────────────────────────────────────────────────────────┘
    
     1. Wafer (웨이퍼)
        ┌───────────┐  - 반도체 칩이 만들어지는 '동그란 실리콘 판 1장'
        │  (  ●  )  │  - 낱개 단위 (최소 실물 단위)
        └───────────┘
    
             │  25장을 모아서 상자에 담음
             ▼
    
     2. Lot (롯트)
        ┌───────────┐  - 웨이퍼 25장을 FOUP(보호 전용 상자) 1개에 담은 '1 세트'
        │ [■■■■■]  │  - FAB(공장) 내부를 이동하는 '작업 및 관리의 최소 단위'
        └───────────┘  - "오늘 1번 Lot 공정 투입해!" 할 때의 그 묶음
          (FOUP 상자)
    
             이 상자(Lot)가 공장 내 장비들을 순서대로 통과함
             
    ```
    
    ![image.png](image.png)
    

### 핵심 기능

**Wafer 패턴 분석 : 2D 배열 형태의 Wafer에서 공간적 불량 패턴 분석**

- Wafer의 위치·형태·분포 특징을 수치화
- 현재 Wafer와 유사한 과거 Wafer Top-K 검색
- 여러 방법을 비교하여 Wafer 형태를 가장 잘 표현하는 방식 선정

**Lot 분석**

- 검색된 유사 Wafer의 Lot 정보를 분석
- 특정 Lot에 패턴이 집중되는지 확인
- 여러 Lot에서 동일한 패턴이 반복되는지도 확인
- 이를 기반으로 엔지니어가 확인할 **Lot 및 생산 범위 우선순위 제공**

**분산 처리**

- 전체 81만 Wafer의 패턴 정보를 대규모 검색이 가능한 형태로 구축
- Vector DB를 이용한 유사 Wafer 검색
- Spark를 활용하여 대규모 검색 결과의 Lot별 발생량·집중도 집계
- 데이터 규모와 Worker 수에 따른 처리 성능 비교

### 활용 데이터 — WM-811K

https://www.kaggle.com/datasets/qingyi/wm811k-wafer-map

- 전체 **811,457개 Wafer**
- **46,293개 Lot**
- Lot당 최대 25개 Wafer
- 불량 라벨 약 **2.5만 개**, 미라벨 약 **63만 개**
- `waferMap`, `lotName`, `waferIndex`, `failureType` 제공

실제 데이터를 확인한 결과, **동일 불량이 같은 Lot에서 반복되는 경향**과 일부 불량 유형에서 **같은 Lot 내 Wafer의 형태가 유사한 경향**이 확인됨.

따라서 `유사 Wafer 검색 → Lot 분포 분석 → 조사 범위 축소`라는 서비스 흐름을 데이터로 구현할 근거가 있음.

### 고려사항 / Challenge

- **일반 Vision과 차이**: RGB 이미지가 아닌 **Die 상태의 2D 배열 데이터**로, 객체 탐지보다 **위치·분포·형태 등 Spatial Pattern 분석**에 가까움
    
    ![image.png](image%201.png)
    
- **AI 방법 선정**: CNN만 사용하는 것이 아니라 **PCA, Hand-crafted Feature, Embedding 등을 비교**해 유사 패턴 검색에 적합한 방법을 선정
- **데이터 난이도**: **클래스 불균형과 대규모 미라벨 데이터**가 있어 선별, 전처리, 평가 설계 필요
- **도메인 학습**: Wafer Pattern과 Lot 등 **반도체 제조 도메인에 대한 이해 기반으로 문제 재정의, 개발 필요**
- **분산처리 검증**: 실제 Fab의 데이터 누적 환경을 가정하고 **데이터 규모 증가에 따른 분산처리 효과를 실험으로 입증**해야 함
- 프로젝트 가치 : 공개 생산 데이터로 재현하고, Spatial AI와 대규모 분산처리를 직접 구현
    - 선행 연구 충분 : 실제 반도체 산업에서 사용되는 Yield/Defect Analytics 문제

### 시연

```
새로운 Wafer 입력
        ↓
Wafer 형태 분석
        ↓
유사 Wafer Top-K 검색
        ↓
검색 결과의 Lot 분포 분석
        ↓
특정 Lot 집중 / 여러 Lot 반복
        ↓
우선 조사 생산 범위 제공

-> 서비스 평가: 조사 범위를 실제로 줄였는가?
```

    - 적외선 열화상에서 장비의 **공간적인 발열 분포와 국부적인 이상 발열 패턴**을 분석
    - 단순 온도센서로는 알기 어려운 `어느 부품·영역에서 비정상적인 발열이 발생하는지` 파악
    - 열화상 특징과 진동·3상 전류·온도·회전속도 등의 시계열 특징을 결합하는 **Multimodal AI**로 고장 후보 분석
- **분산 처리**
    - 여러 장비에서 지속적으로 발생하는 고주파 진동·전류 데이터와 열화상 스트림을 Kafka를 통해 수집
    - Spark Streaming을 이용해 서로 다른 Sampling Rate의 데이터를 **시간 Window 단위로 동기화·전처리·집계**
    - 장비 수와 데이터 발생량을 증가시키면서 처리량·지연시간·Worker 수에 따른 Speed-up을 측정하여 실시간 분산처리 성능 검증
- **서비스**
    - 단순히 `정상/고장` 여부만 알려주는 것이 아니라 **현재 이상과 관련성이 높은 고장 부품·영역을 우선순위로 제공**
    - 예를 들어 열화상의 베어링 영역 국부 발열과 진동 이상이 동시에 나타나는 경우 **Bearing 영역을 우선 점검 대상으로 제시**
    - AI가 실제 고장 원인을 확정하는 것이 아니라 각 센서에서 나타난 이상 근거와 함께 **엔지니어가 어디부터 확인해야 하는지 점검 범위를 축소하는 의사결정 지원 시스템**
- **시연**
    - 여러 산업장비의 기존 실험 데이터를 실시간 스트림처럼 재생하여 `Thermal/Sensor → Kafka → Spark → Multimodal AI → 점검 우선순위 → Dashboard` 전체 과정을 시연
    - Dashboard에서 열화상 이상 영역, 진동·전류 등의 이상 특징과 함께 `Bearing → Alignment → Rotor` 등의 점검 후보 Ranking 제공
    - 정상 상태와 여러 고장 상태를 순차적으로 재생하면서 **장비 상태 변화에 따라 점검 대상이 달라지는 과정**을 시각적으로 보여줌

## 고려 사항

- **고장 원인 확정의 한계**: 데이터에는 실제 Fault Label은 존재하지만 엔지니어의 정비 과정이나 Repair Action 이력은 포함되어 있지 않음. 따라서 `고장 원인을 자동으로 해결`하는 시스템보다는 **고장 후보 및 점검 영역을 좁혀주는 시스템**으로 정의
- **실제 실시간 데이터가 아님**: 시연에서는 저장된 열화상·센서 데이터를 Timestamp에 따라 재생하여 다수 산업장비에서 데이터가 실시간 발생하는 환경을 시뮬레이션
- **분산처리 당위성**: 단순히 장비 수를 늘리는 것보다 **고주파 진동·전류와 저주파 열화상처럼 Sampling Rate가 서로 다른 대규모 멀티모달 스트림을 실시간 동기화·Window 처리하는 문제**를 중심으로 Kafka/Spark의 필요성을 검증

> **제조·정비 현장에서 모델명이나 Part Number를 알 수 없는 부품을 촬영하면, Vision AI를 활용해 대규모 CAD DB에서 동일·유사한 CAD 모델을 검색하여 부품 식별과 설계 데이터 탐색을 지원하는 시스템**
> 
- 제조·정비 현장에서는 설비에 장착된 부품의 **모델명이나 Part Number를 바로 확인하기 어렵거나, 다른 부품에 가려져 전체 형상을 확인하기 어려운 상황**이 발생할 수 있음.
- 기존 Classification 방식은 `Gear`, `Bearing`, `Bracket`과 같이 부품 종류를 판별할 수 있지만, 실제 필요한 것은 **현재 부품과 일치하거나 가장 유사한 CAD 모델을 찾는 것**
- **Vision AI**
    - 실제 촬영한 부품 이미지와 CAD의 Multi-view Rendering 이미지를 각각 Embedding으로 변환
    - Contrastive Learning 등을 이용해 **실제 사진과 CAD Rendering을 공통 Embedding Space에 매핑**
    - 대규모 CAD Vector DB에서 현재 부품과 동일·유사한 CAD Top-K 검색
    - 촬영 각도 변화 및 일부 가림 상황에서도 동일 CAD를 검색할 수 있도록 **Viewpoint/Occlusion Robust Retrieval** 구현
- **분산 처리**
    - 수십만 개 CAD의 Multi-view Rendering 및 이미지 Embedding을 Spark 기반으로 분산 처리
    - 대규모 CAD 데이터의 Embedding 생성·갱신에 대해 데이터 규모와 Worker 수에 따른 **처리시간·Throughput·Speed-up** 비교
    - 생성된 Embedding을 Vector DB에 저장하여 실시간 유사 CAD 검색
- **서비스**
    - 사용자가 현장에서 부품을 촬영하면 대규모 CAD DB에서 **형상이 가장 유사한 CAD 후보 Top-K** 제공
    - AI가 부품을 단순 카테고리로 분류하는 것이 아니라 **기존 설계 데이터 중 어떤 CAD와 대응되는지 검색**
    - 전체 형상이 보이지 않는 상황에서도 후보를 제공하여 엔지니어의 **부품 식별 및 CAD 탐색 시간 단축**
- **시연**
    - 실제 부품 이미지를 Query로 입력하고 `Vision Encoder → Embedding → Vector DB → CAD Top-K` 검색 과정을 시연
    - 정면/측면 등 **촬영 시점 변화**, 20%·40%·60% **가림 정도**에 따른 Retrieval 성능 비교
    - CAD 데이터 규모 및 Spark Worker 수를 증가시키면서 대규모 Embedding 처리 성능을 비교하여 분산처리 효과 검증

## 고려 사항

- **실제 산업 부품과의 차이**: PrintCAD는 실제 CAD를 3D Printing하여 촬영한 데이터이지만 제조사의 Part Number·재고·정비 이력 등이 연결된 실제 상용 부품 카탈로그 데이터는 아님. 따라서 MVP는 **정확한 상용 부품번호 검색이 아니라 실물 이미지 → 동일·유사 CAD 검색**으로 범위를 설정해야 함.
- **Sim-to-Real Domain Gap**: CAD Rendering과 실제 촬영 이미지 사이에는 배경·조명·재질·반사 등의 차이가 존재하므로 이를 극복하는 것이 핵심 AI 과제.
- **부분 관측 데이터**: 실제로 가려진 부품-CAD Pair가 충분하지 않을 경우 원본 이미지에 다양한 Occlusion을 적용해 부분 관측 상황을 구성하고 가림 정도별 Retrieval 성능을 검증.

> **DRC 위반 발생 시 과거 유사 Repair 사례를 검색하고, 대규모 Repair 이력을 분석하여 설계자가 우선 검토할 수정 방향을 제공하는 시스템**
> 

## 문제 상황

반도체 Physical Design에서 DRC 위반이 발생하면 Layout을 수정하고 다시 검증하는 Rework가 필요하다. 이 과정에서 기존 DRC를 해결하더라도 **주변에 새로운 DRC가 발생하는 Ripple Effect**로 인해 수정과 재검증이 반복될 수 있다.

본 프로젝트는 직접 회로를 자동 수정하기보다, **과거 Repair 경험을 재활용하여 설계자의 수정 방향 선택을 지원**하는 것을 목표로 한다.

## 핵심 기능

- **Vision AI**
    - 현재 DRC 주변 Layout Geometry를 Embedding으로 변환
    - `DRC Rule + Layer + Geometry`가 유사한 과거 Repair 사례 검색
    - 과거의 수정 방법과 성공·실패 결과 제공
- **Repair 의사결정 지원**
    - Repair 방법별 성공률, 기존 DRC 감소량, 신규 DRC 발생률 분석
    - 유사 사례와 통계를 근거로 우선 검토할 Repair 방법 제시
    - AI가 직접 Layout을 수정하지 않고 설계자의 판단을 지원
- **빅데이터 분산처리**
    - 실제 서비스에서 여러 설계 프로젝트의 Repair 경험이 대규모로 축적되는 상황을 가정
    - Spark Batch로 `DRC Rule / Layer / Repair Action / Geometry`별 성공·실패 패턴 분석
    - 데이터 규모와 Worker 수에 따른 분산처리 성능 검증

## 데이터

실제 기능은 [DAC 2026 DRC Benchmark](https://github.com/ASU-VDA-Lab/DAC26_DRC_Benchmark?utm_source=chatgpt.com)와 [EvoDRC](https://github.com/ASU-VDA-Lab/EvoDRC?utm_source=chatgpt.com)의 실제 DRC/Repair 데이터를 활용한다.

빅데이터 처리 검증에서는 실제 Repair 데이터의 구조와 분포를 기반으로 **서비스 확장 상황의 대규모 Repair History를 시뮬레이션**한다.

```
[서비스 검증]
실제 DRC / Repair 데이터
        ↓
Vision AI → 유사 Repair 사례 검색
        ↓
과거 수정 방법 및 결과
        ↓
Repair 방향 의사결정 지원

[빅데이터 검증]
대규모 Repair History
        ↓
Spark Batch
        ↓
Rule / Layer / Action별
성공률·신규 DRC 발생률 분석
        ↓
Repair Knowledge Base
```

## 차별점

기존 DRC Checker:

> **“어떤 설계 규칙을 위반했는가?”**
> 

본 시스템:

> **“과거 유사한 DRC에서는 어떤 Repair를 시도했고, 어떤 방법이 효과적이었는가?”**
> 

즉 **DRC 검사나 자동 수정을 대체하지 않고, 축적된 과거 Repair 경험을 Vision AI와 빅데이터 분석으로 재활용하여 반복적인 Rework의 시행착오를 줄이는 것**이 핵심이다.
