### 1-1. 서버 대수와 역할

현재 구성은 **2대**다. CI 파일의 IP 와 태그에서 확인했다.

| 서버 | 사설 IP | 올라가는 것 | 근거 |
| --- | --- | --- | --- |
| **BE 박스** | `172.26.8.28` | GitLab Runner(`a307-deploy`), nginx, `a307-backend` · **`a307-redis`** 컨테이너 | `.gitlab-ci.yml` `PRIVATE_IP`·`WEB_ROOT` · `docker ps`(09-23) |
| **AI 박스** | `172.26.4.46` | GitLab Runner(`a307-ai-deploy`), `a307-ai` 컨테이너, **PostgreSQL(`a307-db`)** | `.gitlab-ci.yml` `AI_HEALTH`·`deploy-ai` 태그 · `docker inspect a307-db`(09-23) |

> 🔴 **운영 DB 가 AI 박스에 같이 있다.** 그래서 AI 컨테이너에 메모리 상한이 **필수**다.
> CI 주석 원문 — "상한이 없으면 모델이 메모리를 먹다가 DB 를 끌고 내려간다. 그러면 BE 도 같이 죽는다 — `ddl-auto=validate` 라 DB 가 없으면 재기동도 안 된다."

**Redis 는 BE 박스의 컨테이너다** (`a307-redis`, `redis:7-alpine`). 2026-09-23 `docker ps` 로 확인했다.

> 🔴 **포트를 호스트에 내보내지 않는다.** `docker ps` 의 포트 칸이 `6379/tcp` 로만 보인다 — `->` 가 없다.
> 즉 호스트의 6379 에는 아무것도 없고 **`a307-net` 안에서 컨테이너 이름으로만** 닿는다.
>
> 그래서 `application.properties` 의 `spring.data.redis.host=localhost` 로는 운영이 돌 수 없다.
> 컨테이너 안에서 `localhost` 는 그 컨테이너 자신이기 때문이다. 실제로 `/etc/a307/backend.env` 에
> **`SPRING_DATA_REDIS_HOST`** 가 들어 있어 이 값을 덮는다(3-6). 새 서버에 올릴 때 빠뜨리기 쉬운 항목이다.

### 2-1. 계정·키 발급이 필요한 외부 서비스

| 서비스 | 발급물 | 들어가는 변수 | 없으면 |
| --- | --- | --- | --- |
| **카카오 개발자** | REST API 키 (OAuth) | `KAKAO_CLIENT_ID` · `KAKAO_CLIENT_SECRET` | 카카오 로그인만 실패 |
| **카카오 개발자** | REST API 키 (Local API) | `KAKAO_REST_API_KEY` | 위치·정비소 검색 API 503 |
| **카카오 개발자** | **JavaScript 키** | `VITE_KAKAO_JS_KEY` (프론트 빌드) | 지도 화면이 안 뜸 |
| **Google Cloud** | OAuth 클라이언트 | `GOOGLE_CLIENT_ID` · `GOOGLE_CLIENT_SECRET` | 구글 로그인만 실패 |
| **AWS** | S3 버킷 **2개** + IAM 역할 | `STORAGE_STAGING_BUCKET` · `STORAGE_SERVICE_BUCKET` | 이미지 업로드 503 |
| **SSAFY GMS** | GMS 키 | `GMS_KEY` | LLM 기능 전부 503 |

> 🔴 **AWS 자격증명 — 운영은 정적 키를 쓴다.** `build.gradle` 주석과 `backend/.env.example` 은 기본 자격증명 체인(로컬 `aws configure`, 배포 서버는 **EC2 IAM 역할**)을 전제로 쓰였다. 그런데 실제 운영 `/etc/a307/backend.env` 에는 **`AWS_ACCESS_KEY_ID`·`AWS_SECRET_ACCESS_KEY` 가 들어 있다**(2026-09-23 확인, 3-6). 새 서버에 올릴 때도 이 두 값이 필요하다.
>
> **개선 과제** — EC2 IAM 역할을 붙이고 이 두 줄을 지우면 키가 파일에 남지 않는다. 바꾸면 이 문단과 2-3(IAM 권한)도 함께 고친다.

> ⚠️ **카카오 키가 세 종류다.** OAuth 용 REST API 키, Local API 용 REST API 키, 지도용 JavaScript 키. 서버는 JavaScript 키를 보관하지도 응답으로 내보내지도 않는다(`application.properties` 191행 주석).

> 🔴 **구글은 키를 받는 것으로 끝나지 않는다.** OAuth 앱 게시 상태가 **`프로덕션`** 이어야 등록되지 않은 사용자가 로그인할 수 있다. `테스트 중` 이면 테스트 사용자 목록에 있는 계정만 통과하는데, **앱 소유자는 목록에 없어도 로그인되므로 본인 계정으로 성공하는 것은 검증이 아니다.** 새 구글 프로젝트로 옮기면 게시를 다시 해야 한다.
>
> 함정이 하나 있다 — **승인된 도메인에는 하위 도메인을 넣을 수 없다.** `j15a307.p.ssafy.io` 는 거절되고 최상위 비공개 도메인인 `ssafy.io` 를 넣어야 한다. 절차와 확인 방법은 `exec/외부서비스.md` 4절에 있다(2026-09-23 프로덕션 전환·다른 계정 로그인 확인 완료).

### 2-3. 필요한 IAM 권한

`backend/.env.example` 말미에서 그대로 옮겼다. 버킷 2개 모두에 대해:

```
s3:PutObject      presigned PUT · 파생본 저장
s3:GetObject      원본 읽기 · presigned GET(조회 URL)
s3:HeadObject     완료 통보의 3단 재검증(실제 크기 확인)
s3:DeleteObject   이미지 삭제 · 실패분 정리
```

> `s3:GetBucketLocation` 은 **필요하지 않다** — 리전을 코드에서 명시하므로 SDK 가 묻지 않는다.
> 단 `AWS_REGION` 을 **비우면** SDK 가 `GetBucketLocation` 을 부르고, 권한이 없어 `AccessDenied` 로 죽는다.

### 2-5. 미리 만들어 둬야 하는 것 — CI 가 만들지 않는다

```bash
docker network create a307-net
```

**`.gitlab-ci.yml` 에 `docker network create` 가 없다.** `deploy` 잡이 `--network a307-net` 으로 붙기만 한다. 네트워크가 없으면 `docker run` 이 실패하고 배포가 멈춘다.

> **현재 운영 서버의 이력** — 이 네트워크는 **김재원이 손으로 만들었다.** 생성 시각은 `2026-09-16 05:32:04 UTC`, 드라이버는 `bridge` 다(`docker network inspect a307-net`). 자동화된 적이 없으므로 **새 서버에서는 반드시 직접 만들어야 한다.**

### 3-3. 기본값이 `changeme` 인 것 — 뜨는데 쓸 때 실패한다

**이 넷이 가장 위험하다.** 값이 채워져 있는 것처럼 보이고 기동도 성공한다. 사용자가 로그인 버튼을 눌러야 드러난다.

| 변수 | 설정 키 | 기본값 | 증상 |
| --- | --- | --- | --- |
| `KAKAO_CLIENT_ID` | `...registration.kakao.client-id` | **`changeme`** | 기동 성공 → 카카오 로그인 시도 시 인증 실패 |
| `KAKAO_CLIENT_SECRET` | `...registration.kakao.client-secret` | **`changeme`** | 동일 |
| `GOOGLE_CLIENT_ID` | `...registration.google.client-id` | **`changeme`** | 기동 성공 → 구글 로그인 시도 시 인증 실패 |
| `GOOGLE_CLIENT_SECRET` | `...registration.google.client-secret` | **`changeme`** | 동일 |

> **왜 `changeme` 인가** — `application.properties` 32행 주석: "client-id/secret 은 비어 있으면 기동 실패(Boot 4)."
> 즉 비워 두면 못 뜨니까 가짜 값을 넣어 뜨게 한 것이다. **대가는 실패 시점이 기동에서 로그인으로 밀린 것이다.**

**대조 사례** — `KAKAO_REST_API_KEY` 는 일부러 빈 문자열을 기본값으로 뒀다. 주석 원문: "`changeme` 같은 가짜 값을 넣으면 키가 있는 것으로 오인해 `KakaoKeyPresentCondition` 이 빈을 띄우고, 첫 호출에서야 -401 을 받는다."

**배포 직후 확인 방법** — 실제로 로그인해 본다. health 로는 잡히지 않는다.

```bash
curl -sI "https://<도메인>/oauth2/authorization/kakao" | head -3
```

`302` 와 `Location:` 에 카카오 주소가 보여야 한다.

| 🔴 `/etc/a307/backend.env` | **운영 비밀값 24개** (3-6 목록) | **있음** · `0600 root:root` · 저장소 밖 |
| 🔴 `/etc/a307/ai.env` | AI 운영값(`AI_INTERNAL_TOKEN`·`DATABASE_URL`·파이프라인 버전 등) | **있음** · 저장소 밖 |
| GitLab CI/CD Variables | `VITE_API_BASE_URL` · `VITE_KAKAO_JS_KEY` | 있음(번들에 박혀 나가므로 비밀 아님) |

**저장소에 실제 비밀값이 들어 있는 파일은 없다.**

**DB 접속 정보는 정확히 세 곳에 있다.**

| 쓰는 쪽 | 어디에 | 변수 |
| --- | --- | --- |
| 백엔드(운영) | BE 박스 `/etc/a307/backend.env` | `SPRING_DATASOURCE_URL` · `DB_USERNAME` · `DB_PASSWORD` |
| AI 서버(운영) | AI 박스 `/etc/a307/ai.env` | `DATABASE_URL` |
| DB 컨테이너 자신 | AI 박스 `a307-db` 의 환경변수 | `POSTGRES_DB` · `POSTGRES_USER` · `POSTGRES_PASSWORD` (4-0) |

로컬은 `docker-compose.yml` 의 `POSTGRES_*` 와 `backend/.env` 를 쓴다.

**새 서버에 값을 채우는 순서**

1. DB 컨테이너를 만들며 `POSTGRES_*` 를 정한다(4-0)
2. `/etc/a307/backend.env` 에 3-6 의 이름 24개를 채운다 — DB 3개, Redis 호스트, 프록시 헤더 전략, 버킷 4개, AWS 자격증명, OAuth 4개, 카카오·GMS 키, AI 주소·콜백 주소·내부 토큰
3. `/etc/a307/ai.env` 에 AI 필수 3개(`AI_INTERNAL_TOKEN`·`FEATURE_PIPELINE_VERSION_ID`·`DATABASE_URL`)를 채운다. 내부 토큰은 백엔드 `INTERNAL_API_TOKEN` 과 **같은 값**이어야 한다
4. GitLab CI/CD Variables 에 `VITE_API_BASE_URL`·`VITE_KAKAO_JS_KEY` 를 넣는다
5. 7장으로 확인한다 — health 만으로는 어댑터 누락이 드러나지 않는다

## 4. 데이터베이스 구축

### 4-0. 운영 DB 컨테이너 — 실제 구성

`docker-compose.yml` 은 로컬 전용이다. 운영 DB 는 AI 박스에서 컨테이너 하나로 돌고 있고,
2026-09-23 `docker inspect a307-db` 로 구성을 그대로 읽었다.

| 항목 | 값 |
| --- | --- |
| 이미지 | `pgvector/pgvector:pg16` — 로컬과 같은 이미지다 |
| 포트 | `172.26.4.46:5432 → 5432`. **사설 IP 에만 묶는다.** 공인 인터페이스에는 열려 있지 않다 |
| 볼륨 | 이름 있는 볼륨 **`a307-pgdata`** → `/var/lib/postgresql/data` |
| 재시작 | `unless-stopped` |
| 네트워크 | `a307-net` 이 **아니다.** 기본 bridge 이고, 백엔드·AI 는 사설 IP 로 붙는다 |
| 환경변수 | `POSTGRES_DB` · `POSTGRES_USER` · `POSTGRES_PASSWORD` (나머지는 이미지 기본값) |

같은 구성을 새 서버에서 재현하는 명령이다.

```bash
docker volume create a307-pgdata
```

```bash
sudo docker run -d --name a307-db \
  -p 172.26.4.46:5432:5432 \
  -e POSTGRES_DB=a307 \
  -e POSTGRES_USER='<사용자명>' \
  -e POSTGRES_PASSWORD='<비밀번호>' \
  -v a307-pgdata:/var/lib/postgresql/data \
  --restart unless-stopped \
  pgvector/pgvector:pg16
```

> 🔴 **운영에는 `docker-entrypoint-initdb.d` 마운트가 없다.** 로컬(4-5)처럼 스키마가 자동으로 들어가지 않는다. 컨테이너를 띄운 뒤 **4-2 의 순서대로 사람이 넣어야 한다.**

> 🔴 볼륨 이름이 `a307-pgdata` 다. 9-4 의 금지 명령(`docker compose down -v` · `docker system prune -a --volumes`)이 지우는 대상이 바로 이 볼륨이다.

### 4-1. `ddl-auto=validate` 가 무슨 뜻인가

```properties
spring.jpa.hibernate.ddl-auto=validate
```

Hibernate 가 **기동 시점에** 엔티티와 실제 스키마를 대조하고, 하나라도 어긋나면 **애플리케이션 전체가 뜨지 않는다.**

> 🔴 이것이 이 프로젝트 전체 배포 절차의 이유다. 그 API 만 죽는 것이 아니라 **앱 전체**가 안 뜬다. CI 에 마이그레이션 가드가 있는 이유도 이것이다.

### 4-2. 적용 순서

**순서를 틀리면 FK 참조가 없는 테이블을 만들려다 실패한다.** 각 단계에 왜 그 자리인지 적었다.

| # | 작업 | 왜 이 순서인가 |
| --: | --- | --- |
| 1 | `CREATE EXTENSION vector` | `repair_case_roi_embedding.embedding vector(768)` 이 이 타입을 쓴다. 확장이 없으면 DDL 이 타입을 몰라 실패한다 |
| 2 | `A307_ddl_final.sql` (47 테이블) | 모든 것의 기반. DDL 내부도 FK 의존성 순서로 정렬돼 있다(헤더 주석 13단계) |
| 3 | `vehicle_model_seed.sql` | `vehicle` · `repair_case` 가 `model_id` 로 참조한다 |
| 4 | `A307_part_code_seed.sql` | `damaged_part` · `estimate_item` 이 `part_code` 를 참조한다 |
| 5 | `pipeline/sql/002` → `015` (14개) | **번호 순서다.** 뒤 번호가 앞 번호가 만든 컬럼·테이블을 전제한다 |
| 6 | `Docs/Erd/migrations/*.sql` (**14개**, `check-applied.sql` 제외) | **날짜 순서다.** 백엔드 기능별 증분. 가장 최근은 `2026-09-22-analysis-job-selected-part.sql` |

> **5번과 6번의 상대 순서는 결과를 바꾸지 않는다** (2026-09-23 확인). 두 묶음이 건드리는 테이블을 전부 뽑아 비교하면 겹치는 것은 `vehicle_model` 하나뿐인데, 그마저 `pipeline/sql/012` 는 `price_tier` 계열 컬럼을, `Docs/Erd/migrations/2026-09-10-admin-master-and-rules.sql` 은 `version` 컬럼을 더해 서로 다르다. 마이그레이션 쪽에 나오는 `repair_case`·`aihub_*`·`feature_pipeline_version` 은 전부 **주석**이고, 파이프라인 쪽은 `part_code` 를 참조하지만 마이그레이션이 추가한 `code_scope` 는 쓰지 않는다.
>
> 전제는 하나다 — **둘 다 2~4번(기반 DDL·차량 시드·부품 시드) 뒤**여야 한다. 실제로 운영 원장(`/home/ubuntu/.a307-applied-migrations`)에도 두 묶음이 번갈아 적용된 기록이 남아 있다.

### 4-3. 적용 명령

```bash
docker exec -i a307-db psql -U "<DB사용자명>" -d a307 -f /tmp/ddl.sql
```

파일을 컨테이너로 먼저 옮긴다.

한글이 제대로 보이면 인코딩이 정상이다.

### 4-4. 무엇이 빠졌는지 확인하는 스크립트

저장소에 **읽기 전용 점검 스크립트**가 있다.

```bash
docker exec -i a307-db psql -U "<DB사용자명>" -d a307 < Docs/Erd/migrations/check-applied.sql
```

`O = 적용됨`, `X = 미적용` 로 파일별 판정을 표로 준다. **`SELECT` 만 한다 — 아무것도 만들거나 고치지 않는다.**

> 🔴 **`2026-09-12-analysis-stage.sql` 은 멱등이 아니다.** `CREATE TABLE` 에 `IF NOT EXISTS` 가 없어 이미 적용된 DB 에 다시 돌리면 `relation "analysis_stage" already exists` 로 멈춘다. 위 스크립트가 "적용됨" 으로 판정하면 **그 파일은 건너뛴다.**

### 4-5. 로컬 개발 DB

`docker-compose.yml` 이 첫 기동에 1~4번을 자동으로 한다.

```bash
docker compose up -d
```

`docker-entrypoint-initdb.d` 마운트가 파일명 순서로 실행한다 — DDL → 차량 시드 → 부품 시드 → AI-Hub 스테이징.

> 🔴 **되돌릴 수 없는 작업 — 경고.** initdb 는 **데이터 디렉터리가 비어 있을 때만** 실행된다. DDL 이 바뀌어도 반영되지 않는다. 반영하려면:
>
> ```bash
> docker compose down -v
> ```
>
> **이 명령은 볼륨을 지운다. 로컬 DB 의 모든 데이터가 사라진다.**
> 🔴 **운영 DB 가 있는 박스에서는 절대 치지 않는다.** `repair_case` corpus 72만 건이 사라진다.
> 같은 이유로 그 박스에서 `docker system prune -a --volumes` 도 치지 않는다.

## 6. 실행

### 6-1. 백엔드 컨테이너

`.gitlab-ci.yml` 170~183행에서 **그대로** 가져왔다.

```bash
docker run -d --name a307-backend \
  --network a307-net \
  -p 127.0.0.1:8080:8080 \
  -p 172.26.8.28:8080:8080 \
  --env-file /etc/a307/backend.env \
  -e GMS_PROVIDER=OPENAI \
  -e GMS_MODEL=gpt-5.4 \
  -e GMS_OPENAI_API=chat \
  -e REPAIR_CHECKLIST_WORKER_ENABLED=true \
  -e REPAIR_QUESTION_WORKER_ENABLED=true \
  -e ESTIMATE_NARRATIVE_WORKER_ENABLED=true \
  --restart unless-stopped \
  a307-backend:<커밋_SHORT_SHA>
```

| 옵션 | 왜 필요한가 |
| --- | --- |
| `--network a307-net` | 🔴 **CI 가 만들지 않는다.** 서버에 미리 있어야 한다 |
| `-p 127.0.0.1:8080:8080` | nginx 가 이 주소로 프록시한다 |
| `-p 172.26.8.28:8080:8080` | 🔴 **AI 서버가 결과 콜백을 보내는 주소다.** 빼면 콜백이 전부 실패한다 |
| `--env-file /etc/a307/backend.env` | 비밀값. 🔴 **명령줄에 적으면 `ps` 에 보인다** |
| `-e GMS_*` · `-e *_WORKER_ENABLED` | 비밀이 아니라 리뷰 가능하게 CI 에 둔다 |
| `--restart unless-stopped` | 서버 재부팅 시 자동 기동 |
| 태그가 `latest` 가 아님 | 되돌릴 수 있게 커밋 SHA 로 태그한다 |

> 🔴 **`-e` 가 `--env-file` 을 이긴다.** 같은 이름이 두 곳에 있으면 `-e` 값이 쓰인다. 그래서 `backend.env` 에는 위 여섯 이름을 **적지 않는다.** 값을 바꿀 때는 `docker run` 쪽만 고친다.

> 🔴 **`--env-file` 은 컨테이너 생성 시점에만 읽힌다.** `docker restart` 로는 바뀌지 않는다. 반드시 `docker rm -f` 후 다시 `docker run` 해야 한다.

> ⚠️ `/etc/a307/backend.env` 는 `0600 root:root` 라 `ubuntu` 계정이 못 읽는다. 손으로 칠 때는 `sudo docker run` 이 필요하다.

### 6-2. AI 서버 컨테이너

```bash
docker run -d --name a307-ai \
  -p 172.26.4.46:8000:8000 \
  --env-file /etc/a307/ai.env \
  --memory=6g --memory-swap=6g --cpus=3 \
  --restart unless-stopped \
  a307-ai:<커밋_SHORT_SHA>
```

| 옵션 | 왜 필요한가 |
| --- | --- |
| `-p 172.26.4.46:8000:8000` | 사설 IP 에만 묶는다. 공인 인터페이스에 열지 않는다 |
| `--memory=6g --memory-swap=6g` | 🔴 **선택이 아니다.** 이 박스에 PostgreSQL 이 같이 있다. 상한이 없으면 모델이 메모리를 먹다가 DB 를 끌고 내려가고, 그러면 BE 도 같이 죽는다 |
| `--cpus=3` | |
| `--restart unless-stopped` | |

> `--memory-swap` 을 `--memory` 와 **같은 값**으로 두는 것이 핵심이다. 그래야 스왑을 못 쓰고 상한이 실제로 동작한다.

### 6-3. 프론트엔드 정적 배치

```bash
sudo rm -rf /var/www/a307/*
sudo cp -r frontend/dist/* /var/www/a307/
sudo chown -R ubuntu:www-data /var/www/a307
sudo /usr/bin/systemctl reload nginx
```

> **백엔드를 먼저 올리고 프론트를 나중에 교체한다.** 새 프론트가 아직 없는 API 를 부르는 상황을 피한다.

> `chown` 이 필요한 이유 — Runner 가 root 로 돌아 복사본이 root 소유가 된다. 그대로 두면 나중에 `ubuntu` 로 손수 배포할 때 덮어쓰지 못한다.

### 6-4. nginx — 운영 설정 요약

저장소에 없어서 2026-09-23 에 BE 박스에서 읽었다(`sudo nginx -T`). 옮겨 심을 때 필요한 부분만 추렸다.

```nginx
# 443 (TLS)
listen 443 ssl;
listen [::]:443 ssl ipv6only=on;
server_name j15a307.p.ssafy.io;
ssl_certificate /etc/letsencrypt/live/j15a307.p.ssafy.io/fullchain.pem;

root /var/www/a307;
location / { try_files $uri $uri/ /index.html; }          # SPA 딥링크
location /api/          { proxy_pass http://127.0.0.1:8080; include /etc/nginx/a307-proxy.conf; }
location /oauth2/       { proxy_pass http://127.0.0.1:8080; include /etc/nginx/a307-proxy.conf; }
location /login/oauth2/ { proxy_pass http://127.0.0.1:8080; include /etc/nginx/a307-proxy.conf; }

# 80 — 같은 server_name 으로 받는다
listen 80;
listen [::]:80;
```

`/etc/nginx/a307-proxy.conf` 는 네 줄이다.

```nginx
proxy_set_header Host              $host;
proxy_set_header X-Real-IP         $remote_addr;
proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
```

| 헤더 | 하는 일 |
| --- | --- |
| `Host` | 백엔드가 원래 호스트명을 알게 한다. OAuth 리다이렉트 URI 가 여기서 만들어진다 |
| `X-Real-IP` · `X-Forwarded-For` | 클라이언트 IP 전달. **감사 로그는 이 값을 믿지 않는다**(`AuditLogService` 주석 — 프록시 신뢰 설정이 없으면 클라이언트가 적은 값이 감사 근거가 된다). 읽는 곳은 OAuth 실패 핸들러뿐이다 |
| `X-Forwarded-Proto` | 🔴 **`SERVER_FORWARD_HEADERS_STRATEGY`(3-6)와 짝이다.** 둘 중 하나라도 빠지면 백엔드가 자기를 http 로 알아 로그인 리다이렉트 URI 를 `http://` 로 만들고, 카카오·구글이 `redirect_uri mismatch` 로 거절한다 |

**TLS 인증서** — Let's Encrypt 다. 인증서는 `/etc/letsencrypt/live/j15a307.p.ssafy.io/` 에 있고, 갱신은 **`certbot.timer` 가 자동으로** 한다(2026-09-22 16:32 UTC 실행, 다음 09-23 09:35 UTC). 별도 크론이나 수동 갱신 절차는 없다.

```bash
sudo certbot certificates          # 만료일 확인
systemctl list-timers | grep -i certbot
```

## 7. 기동 확인

### 7-1. health 만 봐서는 안 되는 이유

```bash
curl -sf http://127.0.0.1:8080/actuator/health
```

이것은 **"프로세스가 떴다"** 까지만 보증한다.

> 🔴 `backend/Dockerfile` 과 `.gitlab-ci.yml` 이 같은 경고를 적어 뒀다 — **"어댑터가 없어도 UP 이 뜬다."**
> S3 버킷이 비어 있어도, GMS 키가 없어도, 카카오 키가 `changeme` 여도 `UP` 이다. 그 기능을 실제로 불러야 드러난다.

### 7-2. CI 가 실제로 하는 확인 — 이대로 따라 하면 된다

`.gitlab-ci.yml` 배포 후 확인 단계 그대로다.

```bash
for t in "/ 200 메인페이지" "/mypage 200 SPA딥링크" "/api/guides/checklist 200 공개API" "/api/vehicles/me 401 인증요구"; do
  set -- $t
  code=$(curl -s -o /dev/null -w '%{http_code}' "https://<도메인>$1")
  [ "$code" = "$2" ] && echo "  OK   $3 ($code)" || echo "  실패 $3 (기대 $2, 실제 $code)"
done
```

| 확인 항목 | 기대 응답 | 이것이 검증하는 것 |
| --- | :--: | --- |
| `/` | `200` | nginx + 정적 파일 배치 |
| `/mypage` | `200` | **SPA 딥링크** — nginx fallback 설정이 맞는지 |
| `/api/guides/checklist` | `200` | 백엔드 + DB 연결 |
| `/api/vehicles/me` | **`401`** | 🔴 **Security 가 살아 있는지.** 200 이 나오면 인증이 뚫린 것이다 |

### 7-3. AI 서버 확인

```bash
curl -s http://172.26.4.46:8000/health
```

```bash
H=$(curl -s http://172.26.4.46:8000/health)
echo "$H" | grep -q '"status":"ok"'      || echo "status 가 ok 가 아니다"
echo "$H" | grep -q '"configured":true'  || echo "환경변수 누락 — /etc/a307/ai.env 확인"
echo "$H" | grep -q '"dbReachable":true' || echo "DB 에 닿지 못한다 — DATABASE_URL 확인"
```

응답에 담기는 필드 (`AI/server/app/api/routes.py`):

| 필드 | 판정에 쓰나 | 의미 |
| --- | :--: | --- |
| `status` | 🔴 예 | 항상 `ok` |
| `configured` | 🔴 예 | `AI_INTERNAL_TOKEN` 있고 `FEATURE_PIPELINE_VERSION_ID > 0` |
| `dbReachable` | 🔴 예 | DB 접속 성공 |
| `modelsLoaded` | ❌ **아니오** | 🔴 **기동 직후 `false` 가 정상이다** |
| `embeddingModelLoaded` | ❌ 아니오 | 동일 — 지연 로드 |
| `partWeightsPresent` | 참고 | 가중치 파일 존재 |
| `damageWeightsPresent` | 참고 | 동일 |
| `embeddingConfigured` | 참고 | `DATABASE_URL` 유무 |

> 🔴 **`modelsLoaded` 로 기동을 판정하지 말 것.** YOLO·DINOv2 는 지연 로드라 첫 추론 때 올라온다. 기동 직후 `false` 는 **정상**이다.

### 7-4. 3-3 의 `changeme` 확인 — 별도로 해야 한다

```bash

curl -sI "https://<도메인>/oauth2/authorization/google" | head -3
```

## 8. 자동 배포 (CI/CD)

### 8-1. 구성

```
stages: [ guard, deploy ]

guard  ─ migration-guard   (tag: a307-deploy)
deploy ─ deploy            (tag: a307-deploy)      BE + FE
       └ deploy-ai         (tag: a307-ai-deploy)   AI/** 또는 shared/vision/** 변경 시
```

| 변수 | 값 |
| --- | --- |
| `GIT_DEPTH` | `"0"` — 🔴 얕은 클론이면 guard 의 커밋 비교가 깨진다 |
| `DEPLOY_MARK` | `/home/ubuntu/.a307-deployed-commit` |
| `APPLIED_MIGRATIONS` | `/home/ubuntu/.a307-applied-migrations` |
| `WEB_ROOT` | `/var/www/a307` |
| `HEALTH_URL` | `http://127.0.0.1:8080/actuator/health` |

> **왜 태그를 쓰나** — SSAFY GitLab 에 공용 Runner 가 붙어 있다. 태그가 없으면 공용 Runner 가 작업을 가져가는데 그 Runner 는 우리 서버에 닿지 못해 배포가 실패한다.

**GitLab CI/CD Variables 에 등록할 것은 둘뿐이다.**

| 변수 | 비밀인가 |
| --- | --- |
| `VITE_API_BASE_URL` | 아니다 — 번들에 박혀 브라우저로 나간다 |
| `VITE_KAKAO_JS_KEY` | 아니다 — 동일 |

> 🔴 **백엔드 비밀값을 CI 변수로 옮기지 말 것.** CI 주석 원문 — "파이프라인 로그·아티팩트·포크 MR 로 새어 나갈 경로가 늘어난다."

### 8-2. 멈추는 지점 — 마이그레이션 가드

`Docs/Erd/migrations` 또는 `pipeline/sql` 에 **새 `.sql` 이 생기면 배포를 멈춘다.**

판정 방식: 이전 배포 커밋과 이번 커밋의 diff 로 새 SQL 을 찾고, `<내용 해시> <경로>` 로 만들어 적용 완료 목록과 줄 단위로 대조한다.

> **가드는 DB 를 조회하지 않는다.** 파일 원장만 본다. 그래서 사람이 DB 에 적용한 뒤 **반드시 원장에 적어야 한다.**

> **왜 경로만이 아니라 내용 해시까지 적나** — 적용한 뒤 누가 SQL 을 고치면 다시 멈춰야 하기 때문이다.

**해시는 git blob 해시다** (2026-09-23 확인). 가드는 `git rev-parse "$CI_COMMIT_SHA:$f"` 로 값을 만드는데, 같은 파일에 대해 `git hash-object` 와 값이 같다. 그래서 머지 전에 로컬에서 미리 계산할 수 있다.

```bash
git hash-object Docs/Erd/migrations/2026-09-22-analysis-job-selected-part.sql
```

> **원장은 누적된다.** 같은 파일이라도 내용이 바뀌면 새 해시로 한 줄이 더 쌓인다. 실제로 `check-applied.sql` 은 원장에 여러 줄 들어 있다. 옛 줄을 지울 필요는 없다 — 가드는 "이 줄이 목록에 있는가" 만 본다.

### 8-3. 멈췄을 때 푸는 순서

각 단계에 왜 그 자리인지 적었다.

| # | 작업 | 왜 이 순서인가 |
| --: | --- | --- |
| 1 | **운영 DB 에 그 SQL 을 적용한다** | 🔴 되돌릴 수 없다. 적용 전에 `check-applied.sql` 로 현재 상태를 먼저 본다 |
| 2 | BE 박스에서 guard 로그에 찍힌 `echo` 명령을 **그대로** 붙여넣는다 | 해시가 포함된 줄이라 손으로 쓰면 틀린다 |
| 3 | 파이프라인을 다시 실행한다 | 원장이 갱신돼야 가드가 통과한다 |

```bash
echo '<guard 로그가 출력한 줄 그대로>' >> /home/ubuntu/.a307-applied-migrations
```

> **왜 원장이 필요한가** — CI 주석 원문: "예전에는 '적용 후 다시 실행' 만 안내했는데, 배포가 실패하면 `DEPLOY_MARK` 가 그대로라 다시 실행해도 같은 SQL 이 또 잡혀 **영영 통과하지 못했다.**"

### 8-4. 수동 실행 시 주의

`deploy-ai` 는 `changes:` 조건이 붙어 있다. 그런데 **GitLab 에서 손으로 돌린 파이프라인(New pipeline)에는 비교할 이전 커밋이 없어 `changes` 가 참으로 평가된다.**

> ⚠️ **수동 실행하면 AI 도 같이 재배포된다.** 3.56GB 이미지를 다시 만든다.

### 8-5. 파이프라인에 없는 것

| --- | --- |
| 테스트 잡 | **없음** (`-x test`) |

| 보안 스캔 | 없음 |

### 8-6. GitLab Runner

설치 절차는 GitLab 공식 문서를 따른다 — <https://docs.gitlab.com/runner/install/>.
이 저장소가 전제하는 값은 아래뿐이다(2026-09-23 확인).

| 항목 | 값 | 확인 방법 |
| --- | --- | --- |
| 버전 | **19.3.2** (rev 23a5dafc) | `sudo gitlab-runner --version` |

## 9. 되돌리기

### 9-1. 백엔드 — 이전 이미지로

이미지가 커밋 SHA 로도 태그돼 있다.

```bash
docker images a307-backend --format '{{.Tag}}\t{{.CreatedAt}}' | head -10
```

```bash
sudo docker rm -f a307-backend
sudo docker run -d --name a307-backend \
  --network a307-net \
  -p 127.0.0.1:8080:8080 \
  -p 172.26.8.28:8080:8080 \
  --env-file /etc/a307/backend.env \
  -e GMS_PROVIDER=OPENAI \
  -e GMS_MODEL=gpt-5.4 \
  -e GMS_OPENAI_API=chat \
  -e REPAIR_CHECKLIST_WORKER_ENABLED=true \
  -e REPAIR_QUESTION_WORKER_ENABLED=true \
  -e ESTIMATE_NARRATIVE_WORKER_ENABLED=true \
  --restart unless-stopped \
  a307-backend:<되돌릴_SHORT_SHA>
```

> ⚠️ **스키마는 되돌아가지 않는다.** 이전 이미지가 기대하는 스키마와 현재 DB 가 어긋나면 `ddl-auto=validate` 로 **기동이 실패한다.** 마이그레이션이 포함된 배포를 되돌릴 때는 DB 도 함께 고려해야 한다.

> ⚠️ **`docker image prune -f` 가 배포 끝에 돈다.** 참조되지 않는 이미지를 지우므로 되돌릴 대상이 이미 없을 수 있다. 위 `docker images` 로 먼저 확인한다.

### 9-2. AI 서버 — 환경변수만 되돌릴 때

```bash
sudo sed -i 's/^FEATURE_PIPELINE_VERSION_ID=.*/FEATURE_PIPELINE_VERSION_ID=1/' /etc/a307/ai.env
```

```bash
IMG=$(docker inspect -f '{{.Config.Image}}' a307-ai)
sudo docker rm -f a307-ai
sudo docker run -d --name a307-ai \
  -p 172.26.4.46:8000:8000 \
  --env-file /etc/a307/ai.env \
  --memory=6g --memory-swap=6g --cpus=3 \
  --restart unless-stopped "$IMG"
```

> 🔴 **`docker restart` 로는 안 바뀐다.** `--env-file` 은 컨테이너 생성 시점에만 읽힌다.

### 9-3. 프론트엔드 — 이전 커밋으로 다시 빌드

**이전 `dist` 가 서버에 남아 있지 않다.** CI 가 `rm -rf "${WEB_ROOT:?}"/*` 로 지우고 덮는다.
그래서 되돌리기는 "복사"가 아니라 "재빌드"다. Node(운영 기준 v22.23.2)와 두 값
(`VITE_API_BASE_URL`·`VITE_KAKAO_JS_KEY`)이 필요하다.

| # | 작업 |
| --: | --- |
| 1 | 되돌릴 커밋을 고른다 — 배포 이력이 GitLab **환경(production)** 에 커밋 SHA 로 남아 있다 |
| 2 | 그 커밋을 체크아웃한다 |
| 3 | `frontend/.env.production` 을 만든다 (저장소에 없다 — `.gitignore`) |
| 4 | `cd frontend && npm ci && npm run build` |
| 5 | 번들에 값이 박혔는지 확인한다 — `grep -rq "<백엔드_기준_URL>" frontend/dist/assets/` |
| 6 | 정적 배치 — `sudo rm -rf /var/www/a307/*` → `sudo cp -r frontend/dist/* /var/www/a307/` → `sudo chown -R ubuntu:www-data /var/www/a307` → `sudo /usr/bin/systemctl reload nginx` |

> **백엔드를 함께 되돌릴지 먼저 판단한다.** 프론트만 되돌리면 새 화면이 사라질 뿐이지만, 백엔드를 되돌릴 때는 스키마가 함께 걸린다(9-1).

> **즉시 되돌릴 수단은 없다.** 배포 단계에서 기존 `dist` 를 `/var/www/a307.prev` 로 옮겨 두면 복사 한 번으로 끝나지만, 지금 CI 에는 그 단계가 없다. — **개선 여지**

### 9-4. 해서는 안 되는 되돌리기

| 명령 | 왜 안 되나 |
| --- | --- |
| `docker compose down -v` | 🔴 볼륨 삭제. 운영 DB 박스에서 치면 corpus 72만 건이 사라진다 |
| `docker system prune -a --volumes` | 🔴 동일 |
| `git reset --hard` / `git clean` | 작업 중인 변경이 사라진다 |
