# 빅데이터 분산 처리란?
- **대량의 데이터**를 한 컴퓨터가 처리하기 어려울 때 **여러 대의 컴퓨터**가 **데이터를 나누어서 동시에** 처리하도록 하는 기술
    - 데이터가 많아질수록 CPU, 메모리, 디스크의 한계 때문에 처리 시간이 길어지기 때문
    - 여러 컴퓨터가 동시간에 데이터를 처리한다면 전체 처리 시간을 줄일 수 있음
- **Hadoop**이란?
    - 대규모 데이터를 여러 컴퓨터에 **분산 저장**하고 처리하기 위한 **생태계**
    - 구성 요소
        - **HDFS** (Hadoop Distributed File System)
            - 데이터를 여러 서버에 **분산 저장**하는 기술
        - **MapReduce**
            - 데이터를 여러 서버에서 **분산 처리**
            - **Map → Shuffle → Reduce** 단계로 구성
            1. **Map**
                - 데이터를 **여러 서버에** **나누어** 각각 처리
                - **(Key, Value) 쌍**의 형태로 **저장**
                - ex) 과일 별 판매량을 계산할 때
                    - 입력 데이터: (사과, 딸기, 사과, 사과, 오렌지, 사과, 딸기, 오렌지, 딸기)
                    - 서버 1 → (사과, 1), (사과, 1), (딸기, 1) ⇒ Key는 과일 이름, Value는 개수
                    - 서버 2 → (딸기, 1), (오렌지, 1), (오렌지 1)
                    - 서버 3 → (사과, 1), (사과, 1), (딸기, 1)
            2. **Shuffle**
                - **같은 Key를 가진 데이터**끼리 모음
                - ex) 과일 별 판매량 계산
                    - (사과, 1), (사과, 1), (사과, 1), (사과, 1)
                    - (딸기, 1), (딸기, 1), (딸기, 1)
                    - (오렌지, 1), (오렌지, 1)
            3. **Reduce**
                - 모인 데이터들에 대해 **집계**
                - ex) 과일 별 판매량 계산
                    - 사과 → 4개
                    - 딸기 → 3개
                    - 오렌지 → 2개
            - 개수가 아닌 무게의 평균을 구하는 데에도 활용 가능
                - Map의 핵심은 Reduce에서 처리하기 좋은 Key-Value 쌍으로 변환하는 것
                - ex) 입력 데이터: (사과, 딸기, 사과, 사과, 오렌지, 사과, 딸기, 오렌지, 딸기)
                    1. Map
                        - 서버 1 → (사과, 100), (사과, 150), (딸기, 20) ⇒ Key는 과일 이름, Value는 개수
                        - 서버 2 → (딸기, 25), (오렌지, 100), (오렌지 120)
                        - 서버 3 → (사과, 120), (사과, 130), (딸기, 30)
                    2. Shuffle
                        - (사과, 100), (사과, (150), (사과, 120), (사과, 130)
                        - (딸기, 20), (딸기, 25), (딸기, 30)
                        - (오렌지, 100), (오렌지, 120)
                    3. Reduce
                        - 사과 → (100+150+120+130)/4 = 125
                        - 딸기 → (20+25+30)/3 = 25
                        - 오렌지 → (100+120)/2 = 110
                - Map 단계에서 무게와 개수를 한 번에 전달할 수도 있음 (ex: (사과, 100, 1))
            - **MapReduce 설계 순서**
                1. 최종적으로 구하고 싶은 결과값 선정 (ex: 상품 별 판매량)
                2. 데이터를 묶을 Key(카테고리) 선정 (ex: 상품 ID)
                3. Reduce에서 해야 하는 연산 정의 (ex: 합계 계산)
                4. Map에서 전달해야 하는 Value 정의 (ex: 개별 상품 개수 1)
    - 다양한 분산 처리 기술
        - HDFS → 대용량 데이터 분산 저장
        - Hadoop MapReduce → 분산 배치 처리
        - Apache Spark → 빠른 분산 데이터 처리 (데이터를 메모리에 유지하면서 연산)
        - Kafka → 대규모 데이터 스트리밍
        - Hive → SQL 기반 빅데이터 분석
        - Flink → 실시간 스트림 처리
        - Presto/Trino → 분산 SQL 분석

# 빅데이터 분산 프로젝트에 적합한 주제
- 데이터가 많이 발생하는 문제 상황에 대한 배경이 필요
    - 하루에 GB, TB, 수억~수십억 건의 데이터가 발생하는 도메인
    - ex) 제조 데이터(온도, 압력, 전류, 생산량 등), 교통(차량, GPS, 도로 센서 등), 이커머스(사용자 조회, 장바구니, 구매, 검색 등), 영상/이미지(CCTV, 유튜브, 방송 등)
- 처리해야 할 연산이 많은 경우
    - 집계, 정렬, 통계, 로그 분석, 전처리 등
- 분산 처리의 효과를 입증할 수 있는 문제
    - 처리 시간, 처리량, 확장성, 비용 등

# 빅데이터 분산 기술 활용의 적절성
- 유입 속도 > 단일 노드 처리량: 초당 들어오는 양이 한 대의 디코딩·추론 처리량을 넘을 때
- 항목당 연산이 무겁고 항목 간 독립적: 이미지 1장당 수백 ms~수 초 걸리는 처리 → 완전 병렬화 가능 (embarrassingly parallel)
- 전량 재처리(backfill) 요구: 모델이나 로직이 바뀌면 축적된 전체를 다시 돌려야 함 → 단발 처리와 파이프라인을 가르는 결정적 요건
- 팬아웃: 입력 1개 → 파생물 N개

## Q&A
- 데이터를 저장할 때 입력 단계부터 데이터를 카테고리 별로 각각의 서버에 저장하지 않고 랜덤하게 저장하는 이유
    - 데이터가 어떤 카테고리에 속하는 지 입력 단계에서 알고 있거나 해당 기준대로 균등하게 배치할 수 있다는 보장이 없기 때문
        - 실제 데이터의 경우 카테고리가 수십억 개의 종류를 가질 수도 있는데 그만큼 각각의 서버를 둘 수 없음
        - 데이터 편중 문제: A 상품 9억 건, B 상품 5000만 건, C 상품 5000만 건이 들어올 때 카테고리 별로 서버를 배정하게 되면 A를 저장한 서버만 과부하가 올 수 있음
    - 카테고리가 바뀌거나 새로운 분석 기준이 생기면 그에 따라서 대응할 수 있어야 함
        - 저장할 때의 분산 기준과 분석 시의 분산 기준이 같을 필요는 없음
    - 따라서 **서버 별로 데이터를 균등하게 분배**하는 것이 중요
- Reduce 단계에서 일반적으로 할 수 있는 연산 및 처리
    - Count → 횟수 구하기
    - Sum → 합계 계산
    - Average → 평균 계산
    - Max/Min → 최댓값, 최솟값 계산
    - Duplication → 중복 제거 (ex: 사용자가 방문한 웹페이지)
    - Top-N → 상위 N개 데이터 집계
    - Filtering → 조건에 따른 분류 및 추출
    - Group Statistics → 통계 요약
    - Text Aggregation → 키워드 빈도 집계
    - Join → 동일한 Key를 이용하여 다른 데이터셋을 결합
- Reduce 단계에서 이미지 데이터와 같은 비정형 데이터를 처리할 수 있는가
    - 처리할 수는 있음. 그러나 적합하다고 보기는 어려움
    - Reduce는 본질적으로 (Key, Value) 형태의 데이터를 다루기에 Value에 해당하는 값이 이미지 데이터와 같은 비정형 데이터일 수 있음
    - Map에서 같은 상품 ID로 할당된 이미지 데이터의 경우 Shuffle에서 (상품 A → 이미지 1, 이미지 2, 이미지 3) 과 같이 모였을 때 Reduce에서 이미지 개수 세기, 중복 이미지 제거, 이미지 크기 통계, 특정 조건의 이미지 선별 등의 연산은 충분히 수행 가능
    - 하지만 더하기, 곱하기, Top-N 등 이미지 데이터와 적합하지 않은 연산을 활용할 경우 연산을 통해 나오는 결과물에 대해 의미를 찾기 어려움
        - 컴퓨터 입장에서 이미지는 결국 2차원 백터 상의 숫자 집합이므로 더하기 연산을 할 수는 있지만 해당 연산의 목적이 있어야 의미가 있음 (ex: 이미지의 픽셀을 더해서 평균을 내는 연산의 경우 영상 처리 분야에서 노이즈를 줄이는 효과가 있음)
- VLM을 활용하는 방안
    - 100만 장의 이미지를 보유하고 있다고 가정할 때 이미지 100만 장에 대해서 바로 Reduce 연산을 진행하는 것이 아닌 **Map 단계**에서 **이미지 내의 의미있는 정보**를 **추출**하여 텍스트 데이터로 변환
        - ex) image001 → {object: “car”, color: “red”, count: 2}
            
             image002 → {object: “car”, color: “blue”, count: 1}
            
             image003 → {object: “person”, count: 3}
            
             image004 → {object: “car”, color: “blue”, count: 2}
            
             image005 → {object: “car”, color: “blue”, count: 2}
            
    - 이후 Reduce 단계에서 집계 연산을 수행하기가 매우 편리하고 명확한 기준이 생김
        - ex) 자동차 색상 별 등장 횟수 계산
            - Shuffle → (”car”, “red”, 2), (”car”, “blue”, 1), (”car”, “blue”, 2), (”car”, “blue”, 2)
            - Reduce → red: 2, blue: 5
    - 이러한 과정에서 이미지 등의 비정형 데이터는 Value로 직접 전달되는 것이 아닌 원본 이미지는 분산 저장소에 저장되어 있으면서 이미지의 경로 또는 ID를 전달하는 방식으로 구성됨
    - 비정형 데이터에 대해서 VLM을 통해 구조화된 정보로 변환 → 구조화된 정보를 통해 원하는 인사이트 도출
    - 모든 이미지에 대해서 VLM을 적용하는 것이 시간과 자원 소모가 크지 않을까
        - 이미지 데이터가 100만 장이라 가정할 경우 1장 당 1초가 소요된다고 할 때 단일 GPU 서버에서는 11.6일이 소요됨
        - 따라서 VLM 추론 또한 분산하여 병렬적으로 진행해야 함
        - 하나의 Map 작업이 이미지 입력 → VLM 추론 → 구조화 데이터 추출 → (Key, Value) 데이터 저장의 흐름으로 이어질 것
        - 전체 데이터의 특성을 파악하는 목적이라면 전체에 대해서 VLM 추론하기 보다 샘플링을 통해 일부 데이터에 대해서만 진행할 수 있음
- 이미지 데이터가 포함된 멀티모달 데이터를 확보한다면
    - VLM 추론을 진행하지 않아도 되기 때문에 전처리 시간을 줄일 수 있음
    - 이미지에만 존재하는 정보를 추출할 때에만 VLM을 활용하여 구조화된 데이터를 보강할 수 있음
        - ex) 제조 불량 데이터셋에 외관 이미지와 함께 설비 센서 데이터(온도, 압력, 진동 등), 생산 데이터(작업자, 작업 시간, 불량 여부 등)이 주어질 경우 불량 원인 분석을 위해 이미지 데이터에 대해 VLM을 적용하여 “균열 여부”, “표면 상태” 등의 정보를 추출하여 보강
- 실시간성이 반드시 필요한가
    - 분산 처리와 실시간 처리는 기본적으로 다른 개념
        - 분산(배치) 처리의 예시
            1. 제조 설비 데이터를 하루동안 수집
            2. 1억 건 축적
            3. 분산 처리 및 분석
            4. “어제의 완제품 불량률은 3.2%”
        - 실시간 처리의 예시
            1. 초 당 수만~수십만 건의 센서 데이터
            2. Kafka를 통한 실시간 수집
            3. 수 초 이내 분석 진행
            4. “설비 이상 발생”
    - 시연에서 실시간성을 보여주고 싶다면 **과거에 수집된 AI hub 데이터 등에 대해 시간 순서 별로 나열한 후 순차적으로 입력되는 시뮬레이션 방식**으로 보여줄 수 있음
        - 과거에 수집된 데이터를 실시간으로 유입된 것처럼 재현하여 분산 스트리밍 시연
    - 제공하고자 하는 서비스의 의사결정이 얼마나 빨라야 하는지를 판단하여 실시간성 구현 여부 판정
        - 실시간성이 필요한 서비스 → 사고 위험 탐지, 설비 이상 탐지 등
        - 실시간성이 필요하지 않은 서비스 → 생산성 분석, 불량 원인 분석 등
