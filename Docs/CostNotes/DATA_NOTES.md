# 견적 데이터셋 분석 노트 (TS_99. 붙임_견적서.zip)

- 대상 zip: `1.원천데이터_230126_add/TS_99. 붙임_견적서.zip`
- 분석 방법: `zipfile` 모듈로 각 엔트리를 스트리밍 read → 디코딩(UTF-8) → `json.loads`. 압축 해제 없음. 전체 순회(125,006건)는 집계 카운터만 유지하며 9.5초 내 완료.
- 목적: 수리비 산출 로직 설계를 위한 스키마/단가 로직 파악.

## 4. 한 사고 내 동일 부품 다중 라인 여부 — 전체 전수 검사

- **전체 125,006건 중 59,980건(약 48.0%)의 사고에서 동일 `작업항목 및 부품명`이 2회 이상 등장**한다(빈 문자열 제외, 완전 문자열 일치 기준).
- 이는 데이터 오류가 아니라 **하나의 손상 부품에 대해 탈착→작업(오버홀/수리/판금)→도장이 별도 라인으로 분리 기록되는 정상적인 업무 관행**이다.

실제 예시 (근거: `as-0000004.json`):
```
1  뒤범퍼(단독작업)  작업=탈착   공임=55,440
2  뒤범퍼(단독작업)  작업=오버홀  공임=73,920
3  뒤범퍼(단독작업)  작업=수리   공임=297,000
```
→ 부품명 "뒤범퍼(단독작업)"가 **작업 단계별로 3줄**로 나뉘어 있음. `10 U 뒤범퍼(보수) 수용성 작업=도장 공임=388,000`까지 합치면 같은 부품에 대해 실질 4단계 공임이 존재.

실제 예시 2 (근거: `as-0004814.json`):
```
6   후드  작업=판금   공임=56,440
7 U 후드  작업=오버홀  공임=8,300
```

→ **산출 로직에서 "부품당 비용"을 구하려면 `작업항목 및 부품명`으로 group-by 한 뒤 그 그룹 내 모든 라인(공임+부품가격)을 합산**해야 하며, 단순히 라인 1개 = 부품 1개로 취급하면 안 된다. 부품명이 완전 동일 문자열이 아니라 살짝 다른 표기(`"헤드램프(우)"` vs `"헤드램프(우)그린수가 50%청구"` 등, `as-0000005.json`, `as-0000009.json` 예시)로 나뉘는 경우도 있어 **정확한 매칭은 문자열 완전일치만으로는 부족**하고 접두어/부분일치 기반 정규화가 필요할 수 있음(추정).

## 산출 로직에서 주의할 점

1. **`공임 ≈ HQ% × M/H단가`** 관계가 성립한다(검증: `as-0004814.json` No.1 `HQ%1.32 × 탈부착M/H 33,200원 = 43,820원`과 일치). `M/H`는 탈부착/판금/도장 3종류 시급이 `차량정보`에 있고, 각 항목의 `작업` 값(탈착/오버홀/수리 → 판금·탈부착 계열, 도장 → 도장 계열)에 맞는 M/H를 곱해야 한다. 단, **도장(`작업=="도장"`) 항목의 `HQ%`는 시간 단위가 아니라 패널 대비 100% 기준 비율로 보이며**, `도장M/H`가 빈 값("원"만 있고 숫자 없음, `as-0000004.json` 차량정보 참고)인 레코드도 있어 이 경우 역산이 불가능하다(추정 — 도장 단가는 패널 크기별 외부 단가표에 의존할 가능성).
