검색 모듈이 확정한 손상·부품 조건과 화면용 유사 사례를 받아 수리 비용을 산정하는 모듈의 입·출력 형식이다.

> **MVP 최신 기준:** MVP에서는 검색된 참조 사례에서 비용을 실시간 산출한다. 이 문서는
> 운영 안정화 단계의 `repair_cost_stat` 사전 집계 방식을 설명한다. MVP 계약은
> [`견적 산출 입출력 형식_update.md`](견적%20산출%20입출력%20형식_update.md)를 따른다.

## 필수 조건

- 견적 대상은 `searchability: STRICT`인 결과만 사용한다.
- `VECTOR_ONLY`는 부품이 확정되지 않았으므로 견적 항목으로 만들지 않는다.
- `partCode`와 `damageType`은 검색 모듈이 표준화한 값을 그대로 사용한다.
- 비용은 원 단위 정수이며 부가세를 포함하지 않는다.
- 사례가 부족하면 임의의 금액을 만들지 않고 `estimable: false`를 반환한다.
- 심각도는 이번 비용 산정의 하드 필터로 사용하지 않는다.
- 온라인 요청마다 `repair_case_item` 원천 행을 다시 집계하지 않는다.

## 입력

검색 모듈이 `STRICT` 결과를 비용 산출 모듈에 전달한다. 비용 산출 모듈은
`repair_cost_stat`에서 사전 집계된 통계를 한 번에 조회한다.

### 입력할 핵심 값

```
vehicle
partCode
damageType
confidence
detectionIds
fallbackStage
referencedCaseIds
```

### 입력 예시

```json
{
  "vehicle": {
    "modelId": 41,
    "carClass": "Compact",
    "modelYear": 2021
  },
  "parts": [
    {
      "partCode": "REAR_BUMPER",
      "damageType": "Scratched",
      "confidence": 0.9321,
      "detectionIds": ["501:damage:damage-001"],
      "pairStatus": "PAIRED",
      "searchability": "STRICT",
      "fallbackStage": "PRICE_TIER",
      "referencedCaseIds": [121381, 121414]
    }
  ]
}
```

검색 모듈은 비용을 계산하지 않는다. `referencedCaseIds`는 화면에 보여줄
대표 사례이며 항목당 최대 10건으로 제한한다. 비용 통계의 전체 표본 수는
검색 결과가 아니라 `repair_cost_stat.case_count`에서 가져온다.

## 온라인 조회 설계

```text
벡터 검색 ──→ 화면용 대표 사례 ID (최대 10건)
                  │
STRICT 부품·손상·차급 ──→ repair_cost_stat 일괄 조회 ──→ 비용 분포·견적 항목
```

- `repair_case_roi_embedding`은 **유사한 손상 사진을 찾는 용도**다.
- `repair_cost_stat`은 **비용 범위를 계산하는 용도**다.
- `repair_case_item`은 원천 비용 행으로 보존하고, 통계 배치가 갱신할 때만 읽는다.

한 사고에 STRICT 부품이 여러 개여도 부품별로 DB를 반복 조회하지 않는다. 비용 산출
모듈은 `(car_class, part_code, damage_type, repair_method)` 대상들을 한 번에 넘겨
`repair_cost_stat`을 batch 조회한다. 테이블의 유니크 키
`(car_class, part_code, damage_type, repair_method, source)`가 이 조회를 지원한다.

`fallbackStage`는 벡터 검색이 조건을 얼마나 완화했는지를 보관하는 근거이며,
현재 비용 통계의 조회 축은 `carClass`다. `repair_cost_stat`에 모델 차원은 없으므로
비용 통계에 `MODEL` 단계를 적용했다고 표기하지 않는다.

```json

  "refCaseTotal": 18,

      }

```

## 판정 규칙

| 상황 | 반환 |
| --- | --- |
| `STRICT` 결과와 충분한 사례가 있음 | `estimable: true` · `items[]` 작성 |
| 부품이 확정되지 않음 | `estimable: false` · `PART_NOT_RESOLVED` |
| 차량은 유효하지만 손상이 검출되지 않음 | `estimable: false` · `NO_DAMAGE_DETECTED` |
| 사례 수가 기준보다 적음 | `estimable: false` · `INSUFFICIENT_CASES` |
| 견적 불가 | `totals: {}` · `items: []` |

견적이 불가능해도 손상 검출 결과 자체는 `/analyze`의 `imageResults[]`에서 별도로 반환한다.

## 필드 규칙

| 필드 | 설명 |
| --- | --- |
| `partCode` | 표준 부품 코드 |
| `damageType` | `Scratched` · `Separated` · `Crushed` · `Breakage` |
| `repairMethod` | `coating` · `sheet_metal` · `exchange` · `repair` |
| `partCost` | 부품 비용. 해당하지 않으면 `null` |
| `laborCost` | 공임 |
| `paintMaterialCost` | 도장 재료비. 해당하지 않으면 `null` |
| `itemTotal` | 해당 견적 항목의 총액 |
| `costDistribution` | 유사 사례 비용의 P25·중앙값·P75 |
| `fallbackStage` | `MODEL` · `PRICE_TIER` · `ALL` |
| `confidenceGrade` | `HIGH` · `MEDIUM` · `LOW` · `null` |
| `nonEstimableReason` | `PART_NOT_RESOLVED` · `NO_DAMAGE_DETECTED` · `INSUFFICIENT_CASES` · `null` |

`repairMethod` 후보가 여러 개인 손상은 `repairMethodReason.candidates`에 후보를 남긴다.
심각도에 따른 수리 방식 확정 규칙은 별도 합의 전까지 임의로 적용하지 않는다.

`refCaseCount`와 `costDistribution`은 선택된 `repair_cost_stat` 행의
`case_count`, `cost_p25`, `cost_median`, `cost_p75`에서 만든다. `referencedCaseIds`는
벡터 검색의 화면용 대표 사례라 비용 통계 표본 전체와 같을 필요가 없다.

`totals.min`·`totals.max`는 개별 항목의 P25·P75를 합산한 견적 하한·상한이다.
원천 사례의 실제 최솟값·최댓값을 뜻하지 않는다.

## 통계 테이블 전제

비용 산출 전에 다음 두 가지가 준비되어야 한다.

1. `repair_case_item`에서 `repair_cost_stat`을 생성·갱신하는 배치
2. `paint_material_cost_median` 컬럼 추가 및 배치 적재

현재 테이블에는 `part_cost_median`과 `labor_cost_median`만 있고 도장 재료비 중앙값은
없다. 콜백의 `paintMaterialCost`를 통계 기반으로 반환하려면 이 컬럼이 필요하다.

`repair_cost_stat.source`는 반드시 명시적으로 선택한다. 출처 중 사례 수가 큰 행을
조용히 고르는 방식은 사용하지 않는다. AS·SC 통합 통계를 쓸지, 특정 출처만 쓸지는
비용 정책으로 확정한 뒤 배치와 조회 조건에 같은 값을 적용한다.

통계 배치는 `PAIRED`·`STRICT` ROI의 `part_code`·`damage_type`을 기준으로 같은 사례의
`repair_case_item.part_code` 비용 행을 연결한다. 같은 사고에 ROI나 견적 행이 여러 개여도
비용 표본은 `case_id + part_code` 단위로 `repair_method`와 무관하게 모든 포함 비용 행을
합산한다. 한 부품에 판금과 도장이 함께 있는 것은 정상적인 수리 흐름이므로 수리 방식별로
사례를 쪼개지 않는다. 대표 방식은 `exchange > sheet_metal > repair > coating` 우선순위로
고르고, 혼합 방식의 전체 후보는 `repairMethodReason.candidates`에 남긴다.
`REFERENCE_PRICE`, `ANCILLARY`, `NOT_APPROVED` 행은 비용 정책에 따라 제외한다.

## 모듈 연결

검색 모듈은 화면용 유사 사례를 찾고, 비용 산출 모듈은 통계 테이블에서 비용을 조회한다.
비용 계산 책임은 비용 산출 모듈에 있다.

이 형식은 비용 산출 모듈의 내부 함수 계약이다. 모듈끼리 FastAPI를 호출하지 않고,
검색 결과 객체를 함수 인자로 전달한다.

```python
estimate_result = estimate_service.calculate(search_result)
```

개발용 `POST /estimate`는 위 함수를 외부에서 테스트하기 위한 FastAPI 진입점이다.
운영 분석에서는 `/analyze`가 검색 결과를 비용 산출 모듈에 직접 전달한다.
