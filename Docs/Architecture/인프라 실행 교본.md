**확정된 것**

- EC2 **2대**. #1은 FE+BE, #2는 AI 전용
- **S3는 이미 있습니다.** 새로 만들지 않습니다. 버킷 이름만 확인하면 됩니다
- 백엔드는 **단독으로 뜹니다.** AI 서버가 아예 없어도 기동합니다 — 해당 API만 503입니다

**정해진 것**

- ✅ **PostgreSQL은 AI 서버에 둡니다.** (2026-09-14 결정) 위 그림이 그대로 맞습니다.
  근거는 체크리스트 §6-1 — DB의 가장 무거운 손님이 사용자 API가 아니라 **적재 배치**이고,
  BE 박스는 하루에도 수십 번 재배포되는 반면 `repair_case` 125,006건은 다시 만들기 싫은 자산입니다.
  절차는 §4-2를 따릅니다. **BE 박스에 두는 경우의 서술은 이제 해당 없습니다.**

> 🔴 **그래서 추론 컨테이너에 메모리 상한을 겁니다.** 안 걸면 모델이 메모리를 먹다가
> 같은 박스의 PostgreSQL을 끌고 내려갑니다. DB를 AI 박스에 두기로 한 이상 이건 선택이 아닙니다.
> `docker run --memory=4g --memory-swap=4g --cpus=2 ...` — 값은 §0의 2번 스펙을 확인하고 정합니다.

**아직 안 정한 것**

- Redis 위치. 지금은 BE 박스 컨테이너를 가정했습니다.

## 2. 역할 — 서보영 · 김재원

체크리스트 §4가 분담을 정했습니다. **기준은 "각자 EC2 한 대씩"** 입니다.
여기서는 **서보영 님 시점**으로만 옮깁니다.

```
김재원 — AI 박스 (오전)          서보영 — FE+BE 박스 (오후)
  PostgreSQL + pgvector      →     앱 컨테이너 · nginx · TLS
  마이그레이션                      도메인 · CORS
  데이터 적재
        └──────── 선행 조건 ────────┘
```

### 2-1. 🔴 병렬이 아닙니다 — 순서가 있습니다

"각자 1대"라는 말 때문에 **동시에 시작해도 된다고 읽으면 안 됩니다.**

BE는 `ddl-auto=validate` 라서 **DB가 떠 있고 스키마가 맞아야 기동 자체를 합니다.**
김재원의 박스가 서보영 님 박스의 **선행 조건**입니다.
DB가 준비됐다는 신호를 받고 §4-5부터 시작하세요.

§4-1(EC2 접속·Docker·IAM)은 선행 조건이 없으므로 먼저 해 둬도 됩니다.

### 2-2. 하는 것 — FE+BE 박스

| # | 항목 | 이 문서의 절 |
| --- | --- | --- |
| 1 | EC2 접속 · Docker 설치 · IAM 인스턴스 프로파일 | §4-1 |
| 2 | 환경변수 파일 작성 (김재원 템플릿을 받아 채움) | §4-4 |
| 3 | jar 빌드 · 이미지 빌드 · 컨테이너 기동 | §4-5 · §4-6 |
| 4 | nginx 리버스 프록시 + TLS + 도메인 | §4-7 |
| 5 | CORS 확인 | §4-8 |
| 6 | 기동·기능 확인 | 체크리스트 §5 |

### 2-3. 하지 않는 것 — 김재원이 AI 박스에서 합니다

**중복으로 만들지 마세요.**

| 항목 | 누가 |
| --- | --- |
| **PostgreSQL 기동 · 스키마 초기화** (§4-2) | 김재원 — AI 박스 |
| **마이그레이션 적용** (§4-3) | 김재원 — AI 박스 |
| 데이터 적재 (`repair_case` 125,006건) | 김재원 |
| `backend/Dockerfile` · `.dockerignore` | **이미 있습니다** |
| 환경변수 템플릿 | 김재원이 채워 전달 (체크리스트 §3) |
| 배포 스크립트 초안 | 김재원 |

> §4-2·§4-3은 **읽어 두세요.** 직접 하지 않더라도 §6-2·§6-3의 증상이 나오면
> 그쪽이 원인이라는 것을 알아야 김재원에게 정확히 전달할 수 있습니다.

### 2-4. ⚠️ 나눠지지 않는 것 — VPC · 보안그룹 · IAM

**계정 단위지 박스 단위가 아닙니다.** 두 사람이 동시에 고치면 서로 덮어씁니다.
특히 **두 박스 사이 5432를 여는 규칙은 양쪽에 걸리는 일**입니다.

→ **시작 전 30분에 같이 정하고, 규칙 변경은 한 사람이 몰아서 합니다.**

### 2-5. 왜 이렇게 나눴나

원래 취지는 **"팀에 배포할 줄 아는 사람이 둘이 되는 편이 낫다"** 였습니다
(김재원은 FAST에서 배포를 해 봤습니다).

"준비/실행"으로 자르면 김재원이 EC2를 한 번도 안 만집니다. **박스로 자르면 둘 다 만집니다.**
시연 경로 전체(앱·nginx·TLS·CORS)를 서보영 님이 하므로 **원래 취지는 그대로입니다.**

> ✅ **이 분담은 "DB를 AI 박스에 둔다"는 전제 위에 섭니다. 그 전제가 확정됐습니다**(2026-09-14, §0의 4번).
> 그렇게 정한 이유 중 하나는 **BE가 부르는 자체 호스팅 AI 서버가 아직 없다**는 것입니다.
> BE 박스에 DB를 뒀다면 김재원의 박스는 오늘 할 일이 거의 없었을 것입니다.
> `application.properties` 의 외부 주소는 전부 외부 서비스(SSAFY GMS · 카카오)이고,
> 자체 AI를 부르는 설정이 한 줄도 없습니다. 그래서 지금 AI 박스에 올라가는 것은
> **PostgreSQL과 데이터 적재**입니다.

## 3. 🔴 되돌릴 수 없는 것 — 절차보다 먼저 읽습니다

사고는 절차 중간에 납니다. 경고를 뒤에 두면 그때는 이미 늦습니다.

### 3-1. DB를 Docker로 띄운다면 named volume을 반드시 붙입니다

```bash
docker run -d --name a307-db \
  -v a307-pgdata:/var/lib/postgresql/data \   # ← 이 줄이 없으면
  ...
```

없으면 `docker rm` 한 번에 **`repair_case` 125,006건이 사라집니다.**
다시 만들려면 AI 쪽 적재 배치를 처음부터 다시 돌려야 합니다.

로컬 `docker-compose.yml`은 이미 named volume(`a307-pgdata`)을 쓰고 있습니다.
**그 파일은 로컬 개발용입니다** — 포트를 `127.0.0.1`에만 묶어 뒀고 계정도 개발용입니다.
운영에 그대로 쓰지 마세요.

### 3-2. DB가 있는 박스에서 `docker system prune -a --volumes` 를 치지 않습니다

디스크가 부족할 때 반사적으로 치는 명령입니다. **`--volumes`가 붙으면 3-1의 볼륨까지 지웁니다.**
디스크 정리는 이렇게 합니다.

```bash
docker image prune -a          # 이미지만. 볼륨은 건드리지 않는다
docker builder prune           # 빌드 캐시
docker system df               # 무엇이 용량을 먹는지 먼저 본다
```

### 3-3. 보안그룹에서 5432를 `0.0.0.0/0` 으로 열지 않습니다

AI 서버에서 DB가 보여야 하는 건 맞습니다. 그건 **VPC 내부로 푸는 문제**입니다 —
상대 보안그룹 ID나 사설 CIDR을 소스로 지정합니다. 공인 IP로 여는 순간 인터넷 전체에 열립니다.

### 3-4. `.env` 파일을 커밋하지 않습니다

- `.gitignore`에 `.env` · `.env.*` 가 이미 있습니다 (`!.env.example` 만 예외)
- `.dockerignore`에도 `.env` 가 있어 **이미지에도 안 들어갑니다**
- 서버의 실제 파일은 권한을 좁힙니다

```bash
sudo install -d -m 700 /etc/a307
sudo chmod 600 /etc/a307/backend.env
```

컨테이너에는 `--env-file` 로 넘깁니다. **명령줄에 키를 직접 적으면 `ps` 에 그대로 보입니다.**

### 3-5. AWS 액세스 키를 서버에 두지 않습니다

코드가 AWS 기본 자격증명 체인을 씁니다. **IAM 인스턴스 프로파일**을 붙이면
키가 서버에 존재하지 않게 됩니다. 환경변수에도, 파일에도 넣지 마세요 (체크리스트 §3-6).

`~/.aws/` 를 만들 필요도 없습니다.

### 3-6. 마이그레이션을 되돌리는 스크립트는 없습니다

`Docs/Erd/migrations/` 에 롤백 SQL이 없습니다. **적용 전에 백업을 받습니다.**

```bash
# 스키마+데이터 전체
pg_dump "$DATABASE_URL" -Fc -f ~/a307-$(date +%Y%m%d-%H%M).dump

# 되돌리기
pg_restore -d "$DATABASE_URL" --clean --if-exists ~/a307-<타임스탬프>.dump
```

`DATABASE_URL` 은 셸 환경변수로만 둡니다. 히스토리에 비밀번호가 남지 않게
`~/.pgpass`(권한 600)를 쓰거나 `PGPASSWORD` 를 명령 앞에 붙입니다.

## 4. 절차 — 8단계

**순서를 바꾸면 안 되는 곳은 3번 하나입니다.** 나머지는 앞뒤가 바뀌어도 복구됩니다.

각 단계 끝에 **확인**이 있습니다. 확인 없이 넘어가면 어디서 틀렸는지 못 찾습니다.

### 4-1. EC2 접속 · Docker 설치 · IAM

두 대 모두 Docker가 필요합니다. 설치 방법은 OS에 따르므로 여기 적지 않습니다
(`<확인 필요: OS>`).

함께 하는 것.

- BE 서버에 **IAM 인스턴스 프로파일** 부착 (§3-5). S3 staging/service 접근 권한
- 보안그룹 — 443만 인터넷에 엽니다. **8080은 열지 않습니다** (nginx가 `127.0.0.1:8080`으로 붙습니다)

**확인**

```bash
docker run --rm hello-world                     # Docker 동작
aws sts get-caller-identity                     # IAM 역할이 붙었는지 (키 없이 응답이 오면 성공)
```

`aws sts` 가 자격증명 없음으로 실패하면 인스턴스 프로파일이 안 붙은 것입니다.
이 상태로 진행하면 **앱은 뜨는데 이미지 업로드만 실패**합니다.

### 4-2. PostgreSQL 기동 — **AI 서버에서** (김재원 담당)

> ✅ 위치가 정해졌습니다(2026-09-14). **AI 서버**입니다. 서보영 님이 직접 하실 일은 아니지만,
> §6-2·§6-3의 증상이 나오면 여기가 원인이므로 읽어 두세요.

```bash
# AI 서버에서
docker run -d --name a307-db \
  -v a307-pgdata:/var/lib/postgresql/data \
  -p <사설IP>:5432:5432 \
```

- **`-p 0.0.0.0:5432:5432` 로 쓰지 않습니다** (§3-3). 사설 IP에 묶습니다
- 보안그룹은 BE 서버의 보안그룹 ID를 소스로 지정합니다
- 🔴 **추론 컨테이너에 메모리 상한을 겁니다.** 안 걸면 모델이 메모리를 먹다가 DB를 같이 끌고
  내려갑니다. 그러면 **BE도 같이 죽습니다** — `ddl-auto=validate` 라 DB가 없으면 재기동도 안 됩니다
  ```bash
  docker run --memory=4g --memory-swap=4g --cpus=2 ...   # 추론 쪽
  ```

> BE 서버에 두는 선택지는 검토 끝에 **채택하지 않았습니다.** BE 박스는 하루에도 수십 번
> 재배포되는데 `repair_case` 125,006건을 거기 둘 이유가 없고, 어차피 AI 파이프라인이
> DB를 직접 쓰기 때문에 사설 IP 노출은 어느 쪽이든 필요했습니다. (체크리스트 §6-1)

### 4-3. 🔴 마이그레이션 적용 — 앱보다 먼저

#### 왜 먼저인가

`spring.jpa.hibernate.ddl-auto=validate` 입니다. 기동할 때 Hibernate가 엔티티와 실제 스키마를
대조하고, **하나라도 어긋나면 컨텍스트를 만들다 실패합니다.**

그 API만 죽는 게 아닙니다. **앱 전체가 뜨지 않습니다.**

더 나쁜 건 증상입니다. 마이그레이션 누락이든 환경변수 누락이든 **겉보기 증상이
"컨테이너가 떴다가 죽는다" 하나로 같습니다.** 순서를 지키면 이 분기가 아예 생기지 않습니다.

#### 적용

적용 대상 3개와 사전 확인 명령은 **체크리스트 §2에 있습니다.** 여기 옮겨 적지 않습니다.

요약만 하면 — `Docs/Erd/migrations/` 의 3개 중 **미적용인 것만** 적용합니다.
김재원이 오전에 무엇이 미적용인지 확인해 둡니다.

**적용 전에 §3-6의 백업을 먼저 받습니다.**

**확인**

```bash
psql "$DATABASE_URL" -c "\d analysis_stage"
psql "$DATABASE_URL" -c "\d repair_code"
psql "$DATABASE_URL" -c "\d repair_method_rule"
psql "$DATABASE_URL" -c "\d estimate_validation_rule"
psql "$DATABASE_URL" -c "\d accident_image" | grep angle_code
```

다섯 개가 전부 나와야 합니다. 하나라도 `did not find any relation` 이면 §4-6에서 앱이 안 뜹니다.

> `2026-09-12-analysis-stage.sql` 은 `IF NOT EXISTS` 를 **일부러 안 붙였습니다.**
> 이미 있으면 에러로 알려주는 편이 낫다는 판단입니다. 그 에러는 정상이고, 건너뛰면 됩니다.

### 4-4. 환경변수 파일 작성

```bash
sudo install -d -m 700 /etc/a307
sudo -e /etc/a307/backend.env      # 또는 vi 로 만들고 chmod 600
sudo chmod 600 /etc/a307/backend.env
```

**무엇을 넣는지는 체크리스트 §3(환경변수 25개)이 정본입니다.** 여기 옮겨 적지 않습니다.

다만 **컨테이너로 띄울 때만 필요한 두 개**는 빠뜨리기 쉬워 한 번 더 짚습니다.

```
SPRING_DATASOURCE_URL=jdbc:postgresql://<DB호스트>:5432/a307
SPRING_DATA_REDIS_HOST=<Redis호스트>
```

`application.properties` 에 `localhost` 가 **하드코딩**돼 있습니다. 컨테이너 안에서
`localhost` 는 컨테이너 자신이라 DB에 닿지 못합니다. 코드를 고칠 필요는 없고
환경변수가 이깁니다 (체크리스트 §3-1-A).

**형식 주의** — `--env-file` 은 `KEY=VALUE` 만 읽습니다. 따옴표를 값의 일부로 가져가고
`export` 를 못 씁니다. 쉘 스크립트가 아닙니다.

```
# 맞음
CORS_ALLOWED_ORIGINS=https://example.test,https://www.example.test

# 틀림 — 따옴표가 값에 들어갑니다
CORS_ALLOWED_ORIGINS="https://example.test"
```

**확인**

```bash
grep -c '=' /etc/a307/backend.env            # 변수 개수
grep -n 'changeme' /etc/a307/backend.env     # 아무것도 안 나와야 합니다
ls -l /etc/a307/backend.env                  # -rw------- 여야 합니다
```

`changeme` 가 남아 있으면 **앱은 뜨고 로그인 버튼을 눌렀을 때 실패합니다** (체크리스트 §3-3).

### 4-5. jar 빌드 → 이미지 빌드

**두 단계입니다. 순서가 있습니다.**

```bash
cd backend && ./gradlew bootJar -x test
cd .. && docker build -t a307-backend:$(git rev-parse --short HEAD) -f backend/Dockerfile .
```

두 가지를 주의합니다. 둘 다 이 저장소 고유입니다.

1. **jar를 먼저 만듭니다.** 컨테이너 안에서 Gradle을 돌리지 않습니다. 이 개발 환경에서
   컨테이너 egress가 막혀 의존성을 못 받았기 때문입니다 (`backend/Dockerfile` 머리말).
   덕분에 이미지 빌드가 수 초로 끝나고 EC2에 Gradle 캐시가 필요 없습니다.
2. **빌드 컨텍스트가 저장소 루트입니다.** `backend/` 에서 빌드하면 `COPY backend/build/libs/`
   가 실패합니다. `-f backend/Dockerfile .` 의 마지막 `.` 이 컨텍스트입니다.

**태그에 `latest` 만 쓰지 마세요.** 롤백 수단이 사라집니다 (§7-3).

**확인**

```bash
docker images a307-backend                    # 676MB 안팎
docker history a307-backend:<태그> | head     # 레이어가 4개로 나뉘어 있으면 정상
```

### 4-6. 컨테이너 기동

```bash
docker run -d --name a307-backend \
  -p 127.0.0.1:8080:8080 \
  --env-file /etc/a307/backend.env \
  --restart unless-stopped \
  --memory=<확인 필요: BE RAM의 60~70%> \
  a307-backend:<태그>
```

- **`-p 127.0.0.1:8080:8080`** — 외부에 직접 열지 않습니다. nginx가 앞에 섭니다
- **`--memory`** — 컨테이너 상한을 걸어야 `MaxRAMPercentage=75` 가 의미를 가집니다.
  안 걸면 JVM이 호스트 전체 RAM의 75%를 힙으로 잡습니다

**확인**

```bash
docker logs -f a307-backend | grep -E "Started BackendApplication|ERROR|Caused by"
# "Started BackendApplication in N seconds" 가 나와야 합니다 (로컬 실측 8.6초)

curl -s localhost:8080/actuator/health         # {"status":"UP"}
docker inspect --format='{{.State.Health.Status}}' a307-backend   # healthy (90초 후)
```

> 🔴 **`UP` 은 "기동했다" 까지만 뜻합니다.** 어댑터가 없어도 UP이 뜹니다.
> 기능 확인은 **체크리스트 §5** 의 4개 curl로 따로 합니다. 반드시 하세요.

### 4-7. nginx 리버스 프록시 + TLS

`<확인 필요: 도메인>` · `<확인 필요: 인증서 발급 방식>` 이 필요합니다.

**이 저장소에서 반드시 넣어야 하는 헤더가 있습니다.**

```nginx
location / {
    proxy_pass http://127.0.0.1:8080;

    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;   # ← 이 줄이 없으면 소셜 로그인이 깨집니다
    proxy_set_header X-Forwarded-Host  $host;
}
```

`X-Forwarded-Proto` 가 필요한 이유는 §5-7에 있습니다. **헤더만으로는 부족하고
환경변수도 함께 필요합니다.** 반드시 §5-7을 읽으세요.

**확인**

```bash
curl -sI https://<도메인>/actuator/health | head -1     # HTTP/2 200
curl -s  https://<도메인>/api/guides/checklist | head -c 80   # 비인증 공개 API, 200
```

### 4-8. CORS 확인 → 프론트 연결

FE가 아직 없으므로(`frontend` 디렉터리가 저장소에 없습니다) **지금은 preflight만 확인**합니다.

```bash
curl -si -X OPTIONS https://<도메인>/api/vehicles/me \
  -H "Origin: <FE 오리진>" \
  -H "Access-Control-Request-Method: GET" | grep -i "access-control"
```

`Access-Control-Allow-Origin` 에 FE 오리진이 그대로 돌아와야 합니다.
`Access-Control-Allow-Credentials: true` 도 같이 나와야 합니다.

안 나오면 `CORS_ALLOWED_ORIGINS` 오타입니다. **`*` 는 쓸 수 없습니다** —
`setAllowCredentials(true)` 라 스프링이 기동 시점에 거부합니다 (체크리스트 §3-5).

## 5. 이 저장소의 함정

일반 배포 문서에 없는 것들입니다. **모르면 반드시 밟습니다.**
1~7은 체크리스트에도 근거가 있고, **8·9는 이 교본을 쓰면서 코드에서 새로 찾은 것**입니다.

| # | 함정 | 증상 | 왜 |
| --- | --- | --- | --- |
| 1 | `spring.datasource.url` · `spring.data.redis.host` 가 **하드코딩** | `HikariPool-1 - Starting...` 에서 멈췄다가 기동 실패 | 컨테이너 안에서 `localhost` 는 컨테이너 자신. `SPRING_DATASOURCE_URL`·`SPRING_DATA_REDIS_HOST` 로 덮습니다 (체크리스트 §3-1-A) |
| 2 | `ddl-auto=validate` | **앱 전체가 안 뜸** | §4-3 |
| 3 | jar를 **먼저** 만들어야 함 | `docker build` 가 `COPY backend/build/libs/` 에서 실패 | 컨테이너 안에서 Gradle을 돌리지 않습니다 (`backend/Dockerfile` 머리말) |
| 4 | 빌드 컨텍스트가 **저장소 루트** | 같은 `COPY` 실패 | `backend/` 에서 빌드하면 경로가 안 맞습니다 |
| 5 | 어댑터가 없어도 **앱은 뜨고 health는 UP** | 배포는 성공, **특정 API만 503** | 헥사고날 포트가 `Optional`. health로 기능을 판단할 수 없습니다 |
| 6 | 환경변수 4개가 `changeme` | 뜨기는 하는데 **로그인 클릭하는 순간** 실패 | 빈 문자열이 아니라서 "설정됨"으로 오인됩니다 (체크리스트 §3-3) |
| 7 | Swagger가 기본 공개 | 조용히 열려 있음. 증상이 없음 | 기동 로그 경고 2건이 이것입니다 (체크리스트 §3-1-B) |
| **8** | **nginx 뒤에서 `{baseUrl}` 이 내부 주소로 잡힘** | **소셜 로그인이 `redirect_uri_mismatch` 로 실패** | §5-7 |
| **9** | **세션 쿠키가 `SameSite=Lax` · `Secure` 미지정** | **로그인은 됐는데 이후 API가 전부 401** | §5-8 · 조치는 **환경변수 2개**(§5-9) |

### 5-7. 🔴 함정 8 — nginx 뒤 OAuth 리다이렉트

`application.properties:36` 이 이렇습니다.

```
spring.security.oauth2.client.registration.kakao.redirect-uri={baseUrl}/login/oauth2/code/{registrationId}
```

`{baseUrl}` 은 스프링이 **들어온 요청에서** 만듭니다. 그런데 저장소 전체에
**`server.forward-headers-strategy` 설정이 없습니다** (직접 확인했습니다. 기본값은 `NONE`).

그러면 nginx가 TLS를 끊고 `http://127.0.0.1:8080` 으로 프록시했을 때 스프링이 보는 것은
`http` 와 내부 호스트입니다. 카카오·구글에 등록한 `https://<도메인>/login/oauth2/code/kakao`
와 달라져서 **redirect_uri 불일치로 로그인이 실패합니다.**

**조치 — 두 가지를 같이 해야 합니다.**

1. nginx가 `X-Forwarded-Proto` · `X-Forwarded-Host` 를 보냅니다 (§4-7)
2. 환경변수로 스프링이 그 헤더를 신뢰하게 합니다

```
SERVER_FORWARD_HEADERS_STRATEGY=framework
```

> 🔴 **이 변수는 nginx 같은 신뢰할 수 있는 프록시 뒤에서만 켭니다.**
> 앱이 인터넷에 직접 노출된 상태에서 켜면 클라이언트가 `X-Forwarded-Proto` 를 위조해
> 스프링을 속일 수 있습니다. §4-1대로 8080을 외부에 열지 않는 것이 전제입니다.

**이 변수는 함정 9도 절반 해결합니다.** `request.isSecure()` 가 참이 되면서
세션 쿠키에 `Secure` 가 자동으로 붙습니다. → §5-9

**확인**

```bash
curl -sI "https://<도메인>/oauth2/authorization/kakao" | grep -i location
# Location 의 redirect_uri 파라미터가 https://<도메인>/... 여야 합니다.
# http:// 이거나 내부 IP면 위 설정이 안 먹은 것입니다.
```

> 소셜 제공자 콘솔에도 **같은 URI가 등록돼 있어야 합니다.** 양쪽이 글자까지 같아야 합니다.

### 5-8. 🔴 함정 9 — 세션 쿠키가 크로스 오리진에서 안 실립니다

이 서비스는 JWT가 아니라 **서버 세션 + 쿠키**입니다(`SESSION` 쿠키, Redis 저장).

저장소 어디에도 `CookieSerializer` · `SameSite` · `cookie.secure` 설정이 **없습니다**
(직접 확인했습니다). 즉 Spring Session 기본값인 **`SameSite=Lax`** 가 적용되고
`Secure` 플래그도 붙지 않습니다.

**언제 깨지나** — FE 오리진과 BE 오리진이 **서로 다른 사이트**일 때입니다.

| FE ↔ BE 배치 | 결과 |
| --- | --- |
| 같은 도메인, 경로만 분리 (`/` ↔ `/api`) | **문제 없음** |
| 같은 상위 도메인의 서브도메인 (`www.` ↔ `api.`) | **문제 없음** (same-site) |
| **서로 다른 도메인** (예: FE를 별도 호스팅에) | 🔴 **쿠키가 안 실려 API가 전부 401** |
| FE가 `http`, BE가 `https` | 🔴 같은 증상 |

**증상이 고약합니다.** 로그인 자체는 성공하고 리다이렉트도 잘 됩니다. 그 다음 API 호출만
전부 401이라 "인증이 왜 안 되지"로 시간을 씁니다.

**조치 — 코드 변경이 아니라 환경변수입니다**

- **가장 쉬운 길은 같은 도메인에 두는 것입니다.** nginx에서 `/` 는 FE 정적 파일,
  `/api` · `/oauth2` · `/login` 은 백엔드로 보냅니다. 그러면 이 문제가 아예 없습니다
- 다른 도메인이 불가피하면 **환경변수 하나를 더 줍니다.**

  ```
  SERVER_SERVLET_SESSION_COOKIE_SAME_SITE=None
  ```

  Spring Boot 4.1.1이 `server.servlet.session.cookie.same-site` 를
  `DefaultCookieSerializer.setSameSite()` 로 넘깁니다. **`CookieSerializer` 빈을 직접 만들
  필요가 없습니다.** 우리 저장소에 그 빈이 없으므로 자동 구성이 그대로 적용됩니다.

- **`Secure` 는 따로 줄 필요가 없습니다.** `DefaultCookieSerializer` 는
  `useSecureCookie` 가 설정되지 않으면(기본값) **`request.isSecure()` 를 따릅니다.**
  즉 §5-7의 `SERVER_FORWARD_HEADERS_STRATEGY=framework` 를 주면 **Secure가 자동으로 붙습니다.**
  → 함정 8과 9는 같은 뿌리입니다. 아래 §5-9를 보세요.
- FE에서 `fetch`/`axios` 에 `credentials: 'include'` (`withCredentials: true`)가 필요합니다 — FE 몫

> **`SameSite=None` 은 다른 사이트 배치일 때만 줍니다.** 같은 도메인이면 필요 없고,
> 오히려 `None` 은 `Secure` 없이는 브라우저가 거부하므로 TLS가 먼저 서 있어야 합니다.

**확인**

```bash
curl -si "https://<도메인>/api/guides/checklist" | grep -i set-cookie
# SameSite=None 을 준 경우:  Set-Cookie: SESSION=...; Path=/; Secure; HttpOnly; SameSite=None
# 안 준 경우(기본):          Set-Cookie: SESSION=...; Path=/; Secure; HttpOnly; SameSite=Lax
```

배치를 정하고 나서 §0의 5·6번을 채우면 이 판단이 끝납니다.

### 5-9. 함정 8과 9는 같은 뿌리입니다

**변수 하나가 두 함정을 동시에 건드립니다.** 이걸 모르면 함정 8만 고치고
"쿠키에 Secure는 어떻게 붙이지" 로 또 시간을 씁니다.

```
SERVER_FORWARD_HEADERS_STRATEGY=framework
        │
        ├─→ {baseUrl} 이 외부 https 주소로 잡힌다        → 함정 8 해결
        └─→ request.isSecure() 가 true 가 된다
                  └─→ 세션 쿠키에 Secure 가 자동으로 붙는다   → 함정 9 의 절반 해결

SERVER_SERVLET_SESSION_COOKIE_SAME_SITE=None
        └─→ FE·BE 가 서로 다른 사이트일 때만 추가        → 함정 9 나머지
```

**둘 다 환경변수입니다. 월요일 당일에 대응됩니다.**
다만 `SameSite=None` 이 필요한 배치인지는 §0의 5·6번이 정해져야 알 수 있으므로,
**배치를 먼저 정하는 것이 여전히 빠릅니다.**

두 변수는 **체크리스트 §3-1-C** 에도 있습니다. 환경변수 템플릿을 만들 때 그쪽을 보세요.

## 6. 안 될 때 — 증상에서 출발합니다

실제로 보게 되는 건 원인이 아니라 증상입니다.

### 6-1. 컨테이너가 떴다가 바로 죽는다

```bash
docker logs a307-backend 2>&1 | grep -E "Caused by|APPLICATION FAILED" | head -20
```

**마지막 `Caused by` 를 봅니다.** 스택트레이스 맨 위가 아닙니다.

| 로그에 보이는 것 | 원인 | 조치 |
| --- | --- | --- |
| `Schema-validation: missing table` | 마이그레이션 미적용 | §6-3 |
| `Connection refused` · `HikariPool` | DB 주소/보안그룹 | §6-2 |
| `Could not resolve placeholder` | 환경변수 누락 | `--env-file` 경로와 오타 확인 |
| `Failed to bind properties` | `.env` 형식 오류 | §4-4의 따옴표 주의 |
| `Invalid value for cors.allowed-origins` | `*` 를 넣었거나 비었음 | 체크리스트 §3-5 |

### 6-2. `HikariPool-1 - Starting...` 에서 멈춘다

**DB에 못 붙고 있습니다.** 순서대로 좁힙니다.

```bash
# 1) 컨테이너가 보는 주소가 맞는가
docker exec a307-backend env | grep SPRING_DATASOURCE_URL
#    localhost 가 보이면 이것이 원인입니다 (함정 1)

# 2) 호스트에서는 붙는가
psql "$DATABASE_URL" -c "select 1"

# 3) 컨테이너에서 포트가 열리는가
docker exec a307-backend sh -c 'curl -sv telnet://<DB호스트>:5432' 2>&1 | head -3
```

1번이 원인인 경우가 가장 많습니다. 2번이 되는데 3번이 안 되면 **보안그룹**입니다.

### 6-3. `Schema-validation: missing table [...]`

**§4-3을 건너뛰었거나 일부만 적용했습니다.** 로그가 어느 테이블인지 알려줍니다.

```bash
docker logs a307-backend 2>&1 | grep -i "missing table\|missing column"
```

해당 마이그레이션을 적용하고 **컨테이너를 다시 시작**합니다. 이미지는 다시 안 만들어도 됩니다.

```bash
docker restart a307-backend
```

### 6-4. health는 `UP` 인데 특정 API만 503

**정상 동작일 수 있습니다.** 어댑터가 없으면 그 API만 503으로 떨어지는 구조입니다.

```bash
docker exec a307-backend env | grep -E "BUCKET|KAKAO_REST|GMS_KEY|DOCUMENT_STORAGE|ESTIMATE_OCR"
```

체크리스트 §3-2의 표에서 **어느 변수가 어느 기능을 죽이는지** 확인합니다.
**시연에 필요한 API인지 판단이 필요하면 §2-3대로 김재원을 부릅니다.**

### 6-5. 프론트에서 CORS 에러

**서버 로그에는 아무것도 안 남습니다.** 브라우저 콘솔에만 나옵니다.

```bash
curl -si -X OPTIONS https://<도메인>/api/vehicles/me \
  -H "Origin: <FE 오리진>" -H "Access-Control-Request-Method: GET" | grep -i access-control
```

| 결과 | 원인 |
| --- | --- |
| 헤더가 아예 없음 | `CORS_ALLOWED_ORIGINS` 에 그 오리진이 없음 |
| 오리진이 미묘하게 다름 | 끝 슬래시·`www.` 유무·`http`/`https` — **글자까지 같아야 합니다** |
| 앱이 아예 안 떴음 | 기동 시점에 `*` 를 거부합니다. §6-1 |

### 6-6. 로그인은 됐는데 API가 전부 401

**함정 9입니다. §5-8을 먼저 읽으세요.**

```bash
# 1) 쿠키가 내려오는가
curl -si "https://<도메인>/api/guides/checklist" | grep -i set-cookie

# 2) Redis가 살아 있는가 — 세션 저장소입니다
docker exec a307-backend env | grep SPRING_DATA_REDIS_HOST
redis-cli -h <Redis호스트> ping          # PONG
redis-cli -h <Redis호스트> keys 'a307:session*' | head
```

2번에서 키가 안 쌓이면 세션이 저장되지 않는 것이고, 쌓이는데도 401이면 **쿠키가 안 실리는
것(§5-8)** 입니다. 브라우저 개발자도구 Network에서 요청에 `Cookie: SESSION=...` 이
붙는지 보면 바로 갈립니다.

**쿠키가 안 실리는 경우의 조치 — 환경변수입니다.**

```bash
# 3) 지금 쿠키가 어떻게 나가는지 본다
curl -si "https://<도메인>/api/guides/checklist" | grep -i set-cookie
```

| Set-Cookie 에 보이는 것 | 원인 | 조치 |
| --- | --- | --- |
| `Secure` 가 없다 | `request.isSecure()` 가 거짓 — 프록시 헤더를 안 믿고 있다 | `SERVER_FORWARD_HEADERS_STRATEGY=framework` (§5-7) |
| `SameSite=Lax` 인데 FE가 **다른 사이트** | 기본값 그대로 | `SERVER_SERVLET_SESSION_COOKIE_SAME_SITE=None` (§5-8) |
| `SameSite=None` 인데 `Secure` 없음 | 브라우저가 쿠키를 아예 거부한다 | 위 두 개를 **같이** 준다 |
| Set-Cookie 자체가 없음 | 세션이 안 만들어졌다. Redis 확인 (위 2번) | — |

**둘 다 컨테이너 재시작으로 끝납니다. 이미지를 다시 만들 필요가 없습니다.**

```bash
# /etc/a307/backend.env 에 추가한 뒤
docker rm -f a307-backend && docker run -d ... a307-backend:<태그>
```

### 6-7. 소셜 로그인이 `redirect_uri_mismatch`

**함정 8입니다. §5-7을 읽으세요.**

```bash
curl -sI "https://<도메인>/oauth2/authorization/kakao" | grep -i location
```

`redirect_uri` 가 `http://` 이거나 내부 IP면 `SERVER_FORWARD_HEADERS_STRATEGY=framework` 가
빠진 것입니다. `https://<도메인>/...` 인데도 실패하면 **제공자 콘솔의 등록 URI**와 대조합니다.

**같은 변수가 §6-6의 쿠키 `Secure` 문제도 고칩니다.** 둘 다 겪고 있다면 원인이 하나입니다 — §5-9.

### 6-8. 502 Bad Gateway (nginx)

nginx는 살아 있고 백엔드에 못 붙는 상태입니다.

```bash
docker ps --filter name=a307-backend          # 컨테이너가 살아 있는가
curl -s localhost:8080/actuator/health        # 호스트에서 직접
sudo tail -50 /var/log/nginx/error.log
```

| 상황 | 원인 |
| --- | --- |
| 컨테이너가 없음 | §6-1 |
| 컨테이너는 있는데 curl 실패 | 아직 기동 중(90초) 또는 포트 매핑 오타 |
| curl은 되는데 502 | nginx `proxy_pass` 주소 오타 |
| 간헐적 502 | 재배포 중 다운타임. §7-2 |

### 6-9. OOM으로 컨테이너가 재시작을 반복한다

```bash
docker inspect a307-backend --format='{{.State.OOMKilled}} {{.RestartCount}}'
docker stats --no-stream a307-backend
docker logs a307-backend 2>&1 | grep -i "OutOfMemory"
```

JVM이 `-XX:+ExitOnOutOfMemoryError` 라 **OOM이면 일부러 죽습니다.** 반쯤 죽은 채로
health만 통과하는 상태보다 낫다는 판단입니다.

| 확인 | 조치 |
| --- | --- |
| `OOMKilled=true` | `--memory` 가 너무 작습니다. 호스트 RAM의 60~70%로 올립니다 |
| 로그에 `OutOfMemoryError` | 힙 부족. `--memory` 를 올리면 `MaxRAMPercentage=75` 가 따라 올라갑니다 |
| DB와 같은 박스 | **DB가 같이 죽었을 수 있습니다.** §3-1 확인 후 §4-2 (가) 배치를 다시 검토 |

### 6-10. 이미지 업로드만 실패한다 (다른 API는 정상)

```bash
aws sts get-caller-identity                             # 호스트에서 IAM 역할 확인
docker exec a307-backend env | grep -E "BUCKET|AWS_REGION"
```

IAM 인스턴스 프로파일이 안 붙었거나(§4-1) 버킷 이름이 비어 있습니다(체크리스트 §3-2).
**앱은 정상으로 보입니다** — 그 API만 503입니다.

## 7. 평시 재배포와 롤백

배포는 월요일 한 번이 아닙니다. 코드 한 줄 고쳤을 때 무엇을 하나.

### 7-1. 먼저 — 마이그레이션이 새로 생겼는지 봅니다

```bash
git log --oneline <이전배포태그>..HEAD -- Docs/Erd/migrations/
```

**나오는 게 있으면 스키마가 바뀐 배포입니다.** §4-3으로 돌아가 마이그레이션을 먼저 적용합니다.
안 나오면 §7-2로 바로 갑니다.

### 7-2. 일반 재배포

```bash
git pull
cd backend && ./gradlew bootJar -x test
cd .. && docker build -t a307-backend:$(git rev-parse --short HEAD) -f backend/Dockerfile .

docker rm -f a307-backend
docker run -d --name a307-backend \
  -p 127.0.0.1:8080:8080 --env-file /etc/a307/backend.env \
  --restart unless-stopped --memory=<값> \
  a307-backend:$(git rev-parse --short HEAD)
```

**실제로 다시 올라가는 건 9.47MB입니다.** 이미지가 676MB지만 레이어가 나뉘어 있어
코드만 바뀌면 `application` 레이어만 교체됩니다 (체크리스트 §3-7 실측).

`docker rm -f` → `docker run` 사이에 **수 초 다운타임**이 있습니다. 시연 중에는 피하세요.
무중단이 필요하면 포트를 바꿔 새 컨테이너를 띄우고 nginx `proxy_pass` 를 바꾼 뒤 예전 것을
내리면 됩니다.

**확인** — §4-6과 같습니다. 매번 `Started BackendApplication` 을 봅니다.

### 7-3. 🔴 태그 전략 — `latest` 만 쓰면 되돌릴 수 없습니다

```bash
docker build -t a307-backend:$(git rev-parse --short HEAD) -f backend/Dockerfile .
docker tag a307-backend:$(git rev-parse --short HEAD) a307-backend:latest
```

**커밋 해시를 태그로 씁니다.** `latest` 는 편의용 별명일 뿐입니다.

- 어떤 이미지가 어떤 코드인지 추적됩니다
- **이전 이미지가 로컬에 남아 있어 롤백이 `docker run` 한 번입니다**
- `docker image prune -a` 는 **참조되지 않는 이미지를 지웁니다.** 직전 2~3개는 남기세요

### 7-4. 롤백

```bash
docker images a307-backend                   # 이전 태그 확인
docker rm -f a307-backend
docker run -d --name a307-backend \
  -p 127.0.0.1:8080:8080 --env-file /etc/a307/backend.env \
  --restart unless-stopped --memory=<값> \
  a307-backend:<이전 태그>
```

> ⚠️ **스키마가 바뀐 배포는 이미지만 되돌려도 안 됩니다.** 새 마이그레이션이 적용된 DB에
> 옛 엔티티로 붙으면 `ddl-auto=validate` 가 또 막습니다. 그때는 §3-6의 백업으로
> DB까지 되돌려야 하고, **되돌리기 스크립트가 없으므로 백업이 유일한 수단입니다.**

## 8. 이번 배포로 열리지 않는 화면

배포가 성공해도 빈 값인 화면이 있습니다. **설정 문제가 아니라 미구현입니다.**
목록은 **체크리스트 §7** 에 있습니다. 시연 시나리오를 짤 때 빼고 짜야 합니다.

배포 중에 "이 화면이 비어 있는데 내가 뭘 빠뜨렸나" 로 시간을 쓰지 않기 위한 안내입니다.

## 9. 이 문서의 한계

**숨기지 않고 적습니다.**

| 항목 | 상태 |
| --- | --- |
| Docker 빌드·기동·`ddl-auto=validate` 통과 | **로컬 Docker에서 실측했습니다** (체크리스트 §3-7). **EC2에서 확인한 것이 아닙니다** |
| nginx 설정 | **실행해 보지 않았습니다.** §4-7은 이 저장소가 요구하는 헤더에 초점을 맞춘 것이고, 나머지는 일반 설정입니다 |
| 함정 8·9가 **존재한다는 것** (§5-7·§5-8) | **설정이 없다는 사실만 코드로 확인했습니다.** 실제로 로그인이 깨지는 것을 재현하지는 않았습니다 — 도메인 배치가 안 정해졌기 때문입니다 |
| 함정 9의 **조치가 환경변수라는 것** (§5-8·§5-9) | **의존성 jar 바이트코드로 확인했습니다.** ① `spring-boot-session-4.1.1` 의 `SessionAutoConfiguration$ServletSessionConfiguration$EmbeddedWebServerConfiguration` 이 `ServerProperties.getServlet().getSession().getCookie()` 를 읽어 `DefaultCookieSerializer.setSameSite()` 로 넘깁니다. ② `spring-session-core-4.1.1` 의 `DefaultCookieSerializer.isSecureCookie()` 가 `useSecureCookie == null` 이면 `request.isSecure()` 를 반환합니다. ③ 생성자 기본값이 `SameSite=Lax` 입니다. **다만 실제로 그 헤더가 나가는 것을 재현하지는 않았습니다** — 도메인과 TLS가 아직 없습니다 |
| EC2 스펙·도메인·버킷·보안그룹 | **모릅니다.** §0에 `<확인 필요>` 로 비워 뒀습니다. 그럴듯한 기본값을 적지 않았습니다 |
| 마이그레이션 3개의 운영 DB 적용 여부 | **아무도 확인하지 않았습니다.** §4-3의 확인 명령으로 직접 봐야 합니다 |

막히면 §2-3의 네 증상에 해당하는지 보고, 해당하면 김재원을 부르세요.
