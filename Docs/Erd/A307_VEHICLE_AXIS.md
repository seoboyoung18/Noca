# 검색 완화 축 설계 — 차종 · 차급 · 가격대

작성: 김경연(데이터 파이프라인) · 2026-09-17
근거 데이터: `Docs/Erd/차량명칭_표준화_매핑표.xlsx`

## 요약

유사 사례 검색의 완화 단계를 `MODEL → CAR_CLASS → ALL`로 잡아 뒀으나, 두 가지가 확인됐다.
(2026-09-17 현재 구현은 `MODEL → PRICE_TIER → ALL`이다. 아래 §4 참고.)

1. **`car_class`는 수리비를 설명하지 못한다.** 경형(CityCar)만 분리되고 소·중·대는 완전히 겹친다.
2. **`MODEL` 단계는 지금 구현되어 있지 않다.** 적재기가 차종을 넣지 않고, 검색 쿼리에 차량 축이 없다.

대안으로 **가격지수 기반 `PRICE_TIER` 축**을 만들었다. 실측 수리비에서 산출했고 전체 견적서의 96.0%를 덮는다.

## 1. 측정 결과

### 1.1 원천 차종 정보

AI Hub 견적서 JSON **125,006건 전수** 기준이다.

| 항목 | 값 |
|---|---|
| 차량명칭 보유율 | **99.86%** (결측 180건) |
| distinct 차량명칭 | 619종 |
| 시드 `model_name` 일치 | 96종 / 107,343건 (**85.9%**) |
| 상위 30종 / 60종 / 100종 누적 | 77.6% / 90.9% / 95.9% |

차종 정보 자체는 사실상 전건에 있다. 표기가 자유 텍스트일 뿐이다.

```
아반떼AD(16) · 아반떼(20)-CN7 · 아반떼MD(13)   → 모두 '아반떼'
HG그랜져 · 그랜져IG(17)                        → '그랜저'
올 뉴 모닝(11) · 올뉴모닝(15) · 올뉴모닝(17)     → '모닝'
```

### 1.2 `모델` 필드는 차종이 아니라 트림이다

적재기가 `repair_case.model_name`에 넣는 `차량정보.모델` 값은 등급·트림이다.

```
'1.6 GDI 스마트' · '럭셔리' · '프레스티지' · 'LTZ' · '가솔린 트랜디'
```

표본에서 433종, 조합 574개 중 260개가 1회만 등장한다. 축으로 쓸 수 없고,
**화면의 `modelName`에도 이 값이 나가고 있다.**

진짜 차종명은 `차량정보.차량명칭`에 있으며 적재기가 이 키를 읽지 않는다.

### 1.3 `car_class` 대비 가격지수

| car_class | 차량 수 | 지수 중앙값 | 범위 |
|---|---|---|---|
| CityCar | 7 | **0.81** | 0.71 ~ 0.99 |
| Compact | 6 | 1.01 | 0.91 ~ 1.20 |
| Mid-size | 28 | 0.99 | 0.90 ~ **1.29** |
| Full-size | 20 | 1.05 | **0.82** ~ 1.21 |

소·중·대의 중앙값 차이가 6% 이내이고 범위가 포개진다.
Full-size 최저(0.82)가 CityCar 최고(0.99)보다 낮고, Mid-size 최고(1.29)가 Full-size 최고(1.21)보다 높다.

**`car_class`는 "경형이냐 아니냐"에 가까운 이진 변수다.**

차급 정의가 배기량·전장 기준(자동차관리법 시행규칙 별표1)이라 가격대와 축이 다르기 때문이다.
실제로 가격을 가르는 것은 브랜드의 부품가 정책이다.

```
상위  QM6 1.29 · SM6 1.28 · SM7 1.25 · SM5 1.22 · QM3 1.20 · SM3 1.18
하위  스파크 0.71 · 모닝 0.77~0.86 · 프라이드 0.83~0.87
```

소형 SUV QM3(1.20)가 대형 SUV 모하비(0.92)보다 30% 비싸다.

## 2. 가격지수 산출 규칙

견적 총액은 사고 심각도(파손 부위 수)에 좌우되므로 쓰지 않는다.
**같은 부품·같은 작업끼리만** 비교한다.

```text
1) 바스켓 선정
   (출처, 부품명, 작업) 조합 중 15종 이상 차량에서 관측된 것만 사용
   차량과 무관한 정비소 정액 항목은 제외
     — 가열건조비 · 공통시간작업 · 수용성도장 · 휠얼라인먼트 · 폐기물 · 소모품

2) 차량별 비율
   해당 조합에서 그 차량의 중앙값 ÷ 그 조합 전체의 중앙값

3) 지수
   로그비의 중앙값을 지수화. 5개 조합 이상 관측된 차량만 산출
   공임지수 · 부품가지수를 각각 구해 기하평균

기준: 1.00 = 전체 중앙값
바스켓: 공임 416조합 · 부품가 98조합
표본: 견적서 약 4.2만 건 (전체의 1/3, 균등 추출)
산출: 105종 — 전체 건수의 96.0%
```

AS는 `부품가격`·`공임`, SC는 `손해사정후.{부품가격, 공임}`을 읽는다.
SC의 부품비는 `작업`이 빈 행에 별도로 실린다.

### 구간

105종 사분위 기준이다.

| 구간 | 범위 | 차량 수 |
|---|---|---|
| P1 저가 | 지수 < 0.94 | 25 |
| P2 중저 | 0.94 ~ 1.00 | 20 |
| P3 중고 | 1.00 ~ 1.07 | 35 |
| P4 고가 | ≥ 1.07 | 25 |

### 한계

- 지수 범위가 0.71 ~ 1.29로 **최대 1.8배**다. 차량이 수리비를 가르지만 폭이 크지는 않다
- 바스켓 조합이 10개 미만인 차량은 흔들릴 수 있다. 매핑표의 `바스켓 수` 열을 함께 본다
- 표본이 1/3이다. 구간 경계에 걸친 차량은 전수 재산출 시 바뀔 수 있다

## 3. MODEL 축 구현 가능성 — 현재는 불가

### 3.1 막혀 있는 지점 셋

**① `repair_case.model_id`가 채워지지 않는다**

DDL에는 있으나 적재기 `upsert_case`의 INSERT 컬럼 목록에 없다. 전 사례 NULL이다.

```
source, external_ref, manufacturer, model_name, car_class,
model_year, repair_year, labor_rate, total_cost, claim_amount, paid_amount
```

**② `model_name`에 트림이 들어간다**

`vehicle.get("모델")` → `'1.6 GDI 스마트'`. 차종명(`차량명칭`)은 읽지 않는다.

**③ 검색 쿼리에 차량 축이 없다**

`vector_repository._query`의 술어는 셋뿐이다.

```
f.damage_type · f.part_code · c.car_class
```

즉 지금 동작하는 완화는 `CAR_CLASS → ALL` **2단계**다. `MODEL`은 구현된 적이 없다.

### 3.2 필요한 작업

| # | 작업 | 비고 |
|---|---|---|
| 1 | 매핑표 상위 100종 확정 | 사람 검토. 95.9% 커버 |
| 2 | 정규화 함수 코드화 | 규칙 6개. `shared/vision` 또는 파이프라인 |
| 3 | 적재기 수정 — `차량명칭` 읽기, `model_id` 해석, `manufacturer` 분리 | |
| 4 | `repair_case` 백필 | 견적서 JSON만 읽어 UPDATE. **재임베딩 불필요** |
| 5 | 검색 쿼리에 축 추가 + 인덱스 | |
| 6 | 검증 | 단계별 적격 건수 분포 |

**4번이 가벼운 것이 다행이다.** 임베딩은 `repair_case_roi_embedding`에 있고 차량 정보와 무관하므로,
`(source, external_ref)`로 `repair_case`만 UPDATE하면 된다. 전체 재적재가 아니다.

### 3.3 MODEL 축의 구조적 한계

서비스 사용자 차량은 `vehicle_model.model_id`를 갖는다. 코퍼스와 잇는 열쇠도 `model_id`다.
그런데 양쪽 집합이 어긋난다.

- **시드 51종 중 9종은 코퍼스에 0건이다** — 캐스퍼 · 토레스 · XM3 · 스타리아 · 포터2 · K8 · 봉고3 · G90 · 캠리
  데이터셋이 2018~2020년 기준이라 그 이후 출시 차종이 없다.
  **이 차량으로 견적을 요청하면 MODEL 단계는 구조적으로 0건이다.**
- **코퍼스에만 있고 시드에 없는 차종이 14%다** — K7(1,984) · 제네시스(14)+EQ900(1,882) ·
  아이오닉(1,044) · 스토닉(788) · 에쿠스 · 스타렉스 · 크루즈 등.
  `model_id`가 NULL이 되어 MODEL 단계 후보에서 빠진다.

즉 MODEL 축을 붙여도 **신차일수록 무용하고, 코퍼스의 14%가 축에서 제외된다.**

### 3.4 가격대 축이 유리한 이유

| | MODEL | PRICE_TIER |
|---|---|---|
| 코퍼스 커버리지 | 85.9% (시드 매칭분) | **96.0%** |
| 신차 대응 | 유사 사례 0건 | 시드 등록 시 구간 지정으로 즉시 동작 |
| 선행 작업 | 매핑표 확정 + `model_id` 해석 | 매핑표 확정(동일) + 구간 부여 |
| 표본 크기 | 차종 하나로 좁아짐 | 구간당 수십 종이라 최소 건수 확보 쉬움 |

가격대 축은 **표본을 덜 깎으면서 비용 분산을 줄인다.** 최소 적격 사례 5건을 채워야 하는
제약을 생각하면 이쪽이 실용적이다.

## 4. 권고

### 완화 단계

```text
1단계  PRICE_TIER  같은 가격대
2단계  ALL         전체
```

`CAR_CLASS`는 완화 축에서 뺀다 — 경형 외에는 설명력이 없다. `MODEL`은 넣는다.
`repair_case.model_id` 백필이 선행되면 가장 강한 축이고, 백필 전에는 빈 결과로
다음 단계에 넘어가므로 넣어 두어도 동작이 달라지지 않는다.

> **2026-09-17 정정.** 이 절은 원래 "`fallbackStage` enum은 바꾸지 않고 `PRICE_TIER`를
> 추가만 한다"고 적었다. 그대로 두면 화면 문구가 틀린다 — `BasisNarrative`가
> `CAR_CLASS`를 "동일 차급"이라는 사용자 문구로 바꾸기 때문에, 실제로는 가격대로
> 찾아 놓고 "동일 차급 N건 기준"이라고 표시하게 된다. 그래서 **`CAR_CLASS`를
> `PRICE_TIER`로 제자리 rename** 한다.
>
> - `LowConfidenceRule`이 `ordinal`로 판정하므로 자리가 같아야 한다. `MODEL` 다음,
>   `ALL` 앞이라는 위치가 그대로이므로 판정 로직은 손대지 않는다.
> - `CAR_CLASS` 값 자체는 `PRICE_TIER`와 `ALL` 사이에 남긴다. `estimate_item.ref_condition`
>   JSONB에 이미 저장된 옛 행을 읽어야 하기 때문이다. 새로 만들어지지는 않는다.
> - `warn-from-stage=ALL` 설정값은 그대로다. 옛 행의 경고 여부도 변하지 않는다.

### 신차 기본값

`vehicle_model`에 새 차량을 등록할 때 가격대를 지정한다.
기본값은 **같은 제조사·같은 차급 차량들의 지수 중앙값**이 속한 구간으로 둔다.
르노코리아처럼 브랜드 색이 뚜렷한 경우 이 기본값이 잘 맞는다.

### 문서 정정

- `car_class`를 가격 대리 변수로 설명한 곳을 정정한다
- `MODEL` 완화 단계를 "미구현 — 차종 표준화 및 `model_id` 백필 선행 필요"로 표기한다.
  지금은 "동작 예정"처럼 읽혀 비용 담당자가 오해한다

## 5. 남은 결정

1. **가격대 구간 수** — 현재 4구간(사분위). 3구간으로 줄이면 표본이 늘고 해상도가 준다
2. **전수 재산출 여부** — 지수는 1/3 표본 기준이다. 구간 경계 차량이 바뀔 수 있다
3. **시드 추가 범위** — 코퍼스에만 있는 차종(K7 · 아이오닉 · 스토닉 등)을 등록할지.
   "이 차량으로 견적 요청이 들어올 수 있나"로 판단한다
4. **적재기 수정 이슈 소유** — `model_name ← 차량명칭`, `manufacturer` 분리는
   완화 축과 별개로 **화면에 나가는 값이 틀려서** 필요하다
