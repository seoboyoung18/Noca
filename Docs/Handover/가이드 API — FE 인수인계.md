## 0. 먼저 알아야 할 것 세 가지

### 0-1. ★ 이 API 2종은 **인증이 필요 없다** — 지금 바로 호출된다

**차량 API 와 정반대다.** 차량 API 5종은 로그인이 없어 전부 401 이라 FE 가 손도 못 대지만, **가이드 API 2종은 지금 그대로 붙는다.**

```
GET /api/guides/checklist   200   ← 인증 없이 (실측)
GET /api/guides/shooting    200   ← 인증 없이 (실측)
GET /api/vehicles/me        401   ← 대조군
```

세션도 토큰도 필요 없다. `credentials: 'include'` 도 필요 없다. **이 API 는 세션 쿠키를 만들지도 않는다**(응답에 `Set-Cookie` 없음 — 실측).

> 요구사항 18행 비고: *"로그인 없이 열람 가능한 공개 페이지로 제공"*.
> **즉 FE 가 인증 스토리를 기다리지 않고 먼저 만들 수 있는 화면이다.**

### 0-2. 체크리스트 화면은 **지금 만들 수 있다**

**이미지가 하나도 없다.** 체크박스 + 텍스트뿐이라 서버 응답만으로 화면이 완성된다. → 3장

### 0-3. 촬영 가이드 화면은 **아직 못 만든다** — 서버 탓이 아니라 이미지가 없다

API 는 준비됐다. 그런데 **실루엣 오버레이 이미지 16장(승용·SUV × 8방향)과 예시 사진 10장이 존재하지 않는다.**

**서버는 이미지를 주지 않는다.** `overlaySet: "SEDAN"` 이라는 **코드만** 준다. 그 코드로 꺼내 쓸 이미지가 FE 번들에 있어야 하는데, 그게 아직 디자인되지 않았다. → 4-4 · 5장

> **두 화면의 착수 시점이 다르다.** 체크리스트는 오늘, 촬영 가이드는 이미지가 나온 뒤다.

## 2. 공통 응답 봉투와 에러

### 2-1. 성공 봉투 — 항상 `data` 로 감싼다

```json
{ "data": { ... } }
```

**배열이 바로 오지 않는다. `data` 를 한 번 벗겨야 한다.**

| API | 꺼내는 경로 |
|---|---|
| 체크리스트 | `res.data.steps` |
| 촬영 가이드 | `res.data.shots` · `res.data.overlaySets` · `res.data.recommendedCount` |

### 2-2. 에러 — 정상 사용 범위에서는 사실상 없다

**요청 파라미터도 본문도 없으므로 400 이 날 자리가 없다.** 문안 파일이 깨지면 서버가 **기동 자체에 실패**하도록 되어 있어서, 뜬 서버가 500 을 낼 일도 없다.

FE 가 다뤄야 할 것은 **네트워크 실패**뿐이다.

### 2-3. ⚠️ 다만 — 경로·메서드를 틀리면 404·405 가 아니라 **500** 이 온다

**공통 예외 처리의 결함이다. 가이드 API 만의 문제가 아니라 전 API 공통이다.** 실측:

```
GET  /api/guides/nope        → 500   {"error":{"code":"INTERNAL_ERROR", ...}}   (404 여야 함)
POST /api/guides/checklist   → 500   {"error":{"code":"INTERNAL_ERROR", ...}}   (405 여야 함)
```

→ **개발 중 500 이 나오면 서버 장애를 의심하기 전에 URL·메서드 오타를 먼저 확인할 것.** 서버 수정 예정이다.

### 2-4. ⚠️ 응답이 브라우저 캐시에 남지 않는다

시큐리티가 모든 응답에 아래 헤더를 붙인다(실측).

```
Cache-Control: no-cache, no-store, max-age=0, must-revalidate
```

**내용은 완전히 정적인데 매번 새로 받는다.** 화면을 오갈 때마다 요청이 나가므로, **응답을 FE 상태(스토어·React Query 등)에 담아 재사용**하는 편이 좋다. 문안은 서버 재기동 전에는 바뀌지 않는다.

### 2-5. CORS

`http://localhost:5173` **하나만** 허용한다. **FE 개발 서버를 5173 포트로 띄울 것.**

## 3. 체크리스트 화면

### 3-1. 서버가 주는 것 / FE 가 갖는 것

**서버 응답에는 `steps` 밖에 없다.** 와이어프레임의 나머지 텍스트는 전부 FE 몫이다.

| 화면 요소 | 출처 |
|---|---|
| 단계 번호·제목·항목 12개 | **서버** (`data.steps`) |
| 제목 `사고 현장 체크리스트` | **FE 하드코딩** |
| 부제 `현장에서 순서대로 확인하세요. 로그인 없이 이용할 수 있습니다.` | **FE 하드코딩** |
| 우상단 `완료 항목 4 / 12` + 진행 바 | **FE 계산** — 분모는 `steps.flatMap(s => s.items).length` (=12), 분자는 로컬 체크 수 |
| 하단 `체크 상태는 이 브라우저에만 저장됩니다.` | **FE 하드코딩** |
| 버튼 `사진으로 견적 확인하기` | **FE** (사고 접수 흐름으로 이동) |
| GNB 활성 메뉴 `사고 현장 체크리스트` · 우측 `로그인` | **FE** |

> 분모 12를 **하드코딩하지 말 것.** 문안이 늘거나 줄면 서버 응답만 바뀐다.

### 3-2. ★ 완료 체크 상태 — 서버가 저장하지 않는다. 저장 키가 문제다

**저장 방식은 이미 정해져 있다.** 와이어프레임 하단에 그대로 적혀 있다 — *"체크 상태는 이 브라우저에만 저장됩니다."* 서버가 저장하지 않는 것도 맞다(로그인이 없으므로 저장할 회원이 없다).

**문제는 무엇을 키로 쓰느냐다.** `items` 가 **문자열 배열**이라 지금 쓸 수 있는 키는 `단계order` + `배열index` 뿐이다.

```js
const key = `checklist:${step.order}:${itemIndex}`;   // 현재 계약으로 쓸 수 있는 유일한 키
```

⚠️ **문안이 한 글자라도 바뀌거나 항목 순서가 바뀌면 저장된 체크가 엉뚱한 항목에 붙는다.**
문안은 아직 확정본을 다듬는 중이라 이 위험이 실재한다.

→ **서버가 `itemId` 를 추가할지 검토 중이다**(6장 D-5). 확정되면 `items` 가 `[{ id, text }]` 로 바뀐다.
→ **지금은 위 인덱스 키로 진행하되, `items` 를 읽는 부분을 한 군데로 모아 둘 것.** 계약이 바뀌면 그 지점만 고치면 된다.

### 3-3. 와이어프레임에 오타가 있다 — **JSON 이 맞다**

| | 문안 |
|---|---|
| 와이어프레임 1단계 첫 항목 | `바상등을 켰습니다` ❌ |
| **서버 응답 (정답)** | **`비상등을 켰습니다`** ✅ |

**서버 응답을 그대로 쓸 것.** 와이어프레임을 보고 옮겨 적지 말 것.

### 3-4. 문안 규칙 — 임의로 바꾸지 말 것

- **완료형 서술(`~했습니다`)** 을 유지한다. 지시가 아니라 확인이라 권고 책임을 지지 않는다
- **법적 수치·과실·합의·보상 조언·의료 판단을 넣지 않는다.** 서버 테스트가 이를 막고 있다(항목에 숫자가 들어가면 빌드가 실패한다)
- 문안 기준은 손해보험협회·보험사 공개 안내 자료다 (요구사항 18행)

→ **FE 에서 문구를 덧붙이거나 다듬지 말 것.** 필요하면 기획을 거쳐 서버 문안 파일을 고친다.

## 4. 촬영 가이드 화면

### 4-1. ★ `shots` 10개는 한 배열인데, 화면은 두 섹션이다 — `closeUp` 으로 나눈다

와이어프레임 구조:

```
1. 권장 촬영 순서   8장   ← closeUp: false  (order 1~8)
2. 파손 부위 근접 촬영 2장 ← closeUp: true   (order 9~10)
3. 촬영 시 주의사항        ← 서버 응답에 없다 (5-3)
```

```js
const wide     = shots.filter(s => !s.closeUp);   // 8개 — ① ~ ⑧ 번호를 붙인다
const closeUps = shots.filter(s =>  s.closeUp);   // 2개 — 번호 없이 title 만
```

⚠️ **원형 번호 ①~⑧ 은 `closeUp: false` 인 8개에만 붙는다.** `order` 9·10 을 ⑨⑩ 으로 표시하지 말 것 — 와이어프레임에서 근접 2컷은 번호 없이 라벨만 있다.

### 4-2. `angleCode` — 9종 (10개 컷 중 `DAMAGE_CLOSE` 가 2번)

```
FRONT · REAR · LEFT · RIGHT · FRONT_LEFT · FRONT_RIGHT · REAR_LEFT · REAR_RIGHT · DAMAGE_CLOSE
```

- **컷은 10개, 코드는 9종이다.** `order` 9와 10이 둘 다 `DAMAGE_CLOSE` 다
- → **`angleCode` 를 리스트 key 로 쓰지 말 것.** 중복된다. `order` 를 쓸 것
- 이 값은 나중에 업로드한 사진의 각도를 표시하는 데 쓰일 예정이다. **FE 가 임의의 코드를 만들어 쓰지 말 것**

### 4-3. `overlaySets` — 코드 → 실루엣 매핑. **응답을 그대로 쓸 것**

| `vehicleType` | `overlaySet` |
|---|---|
| `SEDAN` | `SEDAN` |
| `SUV` | `SUV` |
| `VAN` | **`SUV`** ← 폴백 |
| `TRUCK` | **`SUV`** ← 폴백 |

실루엣은 **승용·SUV 2종만** 디자인된다. 차량 유형은 4종이라 `VAN`·`TRUCK` 은 갈 곳이 없어 `SUV` 로 폴백한다.

⚠️ **이 매핑을 FE 상수로 하드코딩하지 말 것.** 응답에 담아 보내는 이유가 *"실루엣이 나중에 추가되면 FE 배포 없이 매핑만 바꿔 반영하기 위해서"* 다. 하드코딩하면 그 이점이 사라진다.

```js
const overlayOf = (vehicleType) =>
  overlaySets.find(o => o.vehicleType === vehicleType)?.overlaySet ?? 'SUV';
```

### 4-4. ★ 이미지는 서버가 주지 않는다 — FE 번들에 있어야 한다

**응답에 이미지 URL 이 하나도 없다.** 오버레이도, 예시 사진도 없다.

**의도된 설계다.** 모바일에서 카메라 화면 위에 실시간으로 겹치는 오버레이라 네트워크 왕복을 기다릴 수 없다. 그래서 서버는 **어떤 실루엣을 쓸지 코드로만** 알려주고, 실물은 FE 번들에서 즉시 꺼내 쓴다.

```
서버:  overlaySet = "SEDAN",  angleCode = "FRONT_LEFT"
FE:    assets/overlay/SEDAN/FRONT_LEFT.svg   ← 이 파일을 FE 가 갖고 있어야 한다
```

> 파일 경로·이름 규칙은 정해진 것이 없다. **FE 가 정하면 된다** — 서버가 관여하지 않는다.

### 4-5. ★ 그런데 그 이미지가 아직 없다

| 필요한 것 | 수량 | 상태 |
|---|---:|---|
| 실루엣 오버레이 (승용 · SUV) × 8방향 | **16장** | **없음** — 디자인 미착수 |
| 예시 사진 (8방향 + 근접 2컷) | **10장** | **없음** — 와이어프레임에 자리만 있다 |

요구사항 19행 확인·결정 사항 원문: ***"8방향 실루엣 오버레이 이미지(승용/SUV 2종) 디자인 필요"*** — 미완이다.

**근접 2컷에 오버레이가 필요한지는 미확정이다**(6장). 필요하면 16장이 아니라 20장이 된다.

→ **이미지가 나오기 전까지 이 화면은 완성할 수 없다.** API 연동과 레이아웃까지는 자리표시자로 진행할 수 있다.

### 4-6. `recommendedCount = 10` 은 **권장이지 업로드 상한이 아니다**

- 업로드 **상한**은 이 API 가 정하지 않는다. 업로드 API 계약을 따로 확인할 것
- 이 값으로 **파일 선택 개수를 제한하지 말 것.** 진행 표시(`3 / 10 장 촬영됨`)에 쓰는 값이다
- 10 을 하드코딩하지 말고 `recommendedCount` 를 읽어 쓸 것

## 5. 아직 없는 것

### 5-1. 실루엣 오버레이 16장 · 예시 사진 10장 → 4-5

**촬영 가이드 화면의 실질 블로커다.** 디자인 요청이 선행되어야 한다.

### 5-2. 체크리스트 항목 식별자 → 3-2

현재 계약은 문자열 배열이다. `itemId` 추가 여부가 검토 중이며, 확정되면 **계약이 바뀐다**(6장 D-5).

### 5-3. 촬영 시 주의사항 5개 — **서버 응답에 없다**

와이어프레임 3번 섹션의 문안 5개가 **API 응답에 포함되어 있지 않다.** 문안에 든 수치가 다른 문서와 어긋나 보여 확정을 미뤄 둔 것이다.

**그 수치 문제는 해소됐다** — 두 값은 층이 다르다.

| | 값 | 성격 |
|---|---|---|
| 안내 문구 ⑤ | 1,024 × 768 · 10MB | **안내 권장치** |
| 서버 품질 판정 | 짧은 변 720px | **판정 임계값** |
| 업로드 상한 (스키마) | 20MB | **하드 상한** |

짧은 변 **768 ≥ 720**, 파일 크기 **10MB ≤ 20MB** — 안내가 판정보다 넉넉한 정상 방향이다. 모순이 아니다.

→ **다음 Task 에서 응답에 추가될 예정이다.** 그때 `shots` 옆에 `precautions` 같은 필드가 붙는다(필드명 미정).

**참고 — 와이어프레임의 5개 문안** (아직 서버가 주지 않는다. FE 가 임시로 하드코딩한다면 아래를 쓰되, **서버에 추가되면 그쪽으로 옮길 것**):

```
· 조명이 부족한 곳은 피해 주세요. 실내 주차장이라면 밝은 곳으로 이동해 촬영해 주세요.
· 역광을 피해 주세요. 태양이나 조명을 등지고 촬영하면 손상 부위가 어둡게 나옵니다.
· 흔들림 없이 촬영해 주세요. 초점이 맞지 않은 사진은 분석에서 제외됩니다.
· 과도한 근접은 피해 주세요. 손상 부위와 함께 주변 패널이 함께 보여야 위치를 판단할 수 있습니다.
· 최소 해상도는 장당 1,024 × 768 이상, 파일 크기 10MB 이하를 권장합니다.
```

### 5-4. 업로드 후 품질 판정(재촬영 권유)은 **아직 구현되지 않았다**

요구사항 20행은 *"업로드 후 서버 품질 검사(해상도·블러 판정)에 미달하면 재촬영 권유를 표시한다"* 인데, **판정 로직이 없다.** 임계값만 설정으로 빠져 있고 그 값을 읽어 쓰는 코드가 없다.

→ **재촬영 안내 화면(`Docs/Wireframe/재촬영.png`)은 아직 붙일 API 가 없다.** 이 Epic 이 아니라 이미지 업로드 API 쪽 작업이다.

## 6. 미확정 — 재원님 확인 대기

**임의로 채우지 말 것.**

| # | 미확정 항목 | 지금 문서의 처리 | 정해지면 바뀌는 것 |
|:---:|---|---|---|
| 1 | **체크리스트 항목 식별자** — `items` 를 `[{id, text}]` 로 바꿀 것인가 | 현재 계약(문자열 배열)을 적었다. 인덱스 키로 진행 | **API 계약이 바뀐다.** FE 착수 전에 정하는 편이 낫다 → 3-2 |
| 2 | **`description` 10개 중 8개가 확정본이 아니다** | 서버 응답을 그대로 적었다. `order` 1·9 만 기획 원문이고 나머지 8개는 백엔드가 같은 어투로 쓴 문장이다 | 문구만 바뀐다. FE 는 서버 값을 그대로 쓰므로 **코드 변경 없음** |
| 3 | **근접 2컷에도 오버레이가 필요한가** | 필요 여부를 정하지 않았다 | 디자인 수량 16장 → 20장 |
| 4 | **촬영 가이드 화면이 공개인가 로그인 뒤인가** | **API 는 인증 불필요**(확정). 다만 와이어프레임 GNB 가 `마이페이지` 라 로그인 상태를 전제하는 것으로 보인다. 체크리스트 쪽 GNB 는 `로그인` 이다 | 라우팅·GNB. **API 는 어느 쪽이든 그대로** |
| 5 | **주의사항 5개의 응답 필드명** | 아직 응답에 없다 → 5-3 | 필드 추가 (기존 필드 불변) |
| 6 | **업로드 장수 상한** | 이 API 가 정하지 않는다. `recommendedCount=10` 은 권장치일 뿐 | 업로드 화면의 제한 → 4-6 |

> **FE 가 임의로 정하지 말 것.** 정하지 않은 것은 정하지 않은 채로 재원님에게 되돌아와야 한다.
